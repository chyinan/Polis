## 31. C-SLEEP：休眠、唤醒、暂停与不丢工作

### 31.1 基本承诺 <a id="subsection-31-1"></a>

**没有可执行工作时不启动新模型请求，不让模型轮询。** Employee、收件箱和责任继续存在；可关闭空闲原生会话，持久记忆不能随会话删除。后台测试、监听程序或数据库可能继续占资源，因此睡眠不承诺整机零消耗。

`EmployeeSchedule` 保存调度状态、work_generation、最近核对时间、next_due_at 和暂停原因；Task/Obligation/Routine 才是需要做什么的权威。WorkSignal 是去重后的唤醒提示，不是第二套任务真相。

### 31.2 状态与唤醒资格 <a id="subsection-31-2"></a>

```text
working → quiescing → sleeping
sleeping → wake_pending → admitted → working
sleeping / wake_pending → paused / waiting_quota
paused → 只有显式有效 resume 才重新准入
```

| 事件 | 默认是否产生付费执行 | 说明 |
|---|---|---|
| 准入条件满足的新任务 | 是，在预算/容量允许后 | 身份、期限、依赖必须再次检查 |
| 必须回应的协作请求 | 是或加入当前工作边界输入 | 同问题去重，不能被垃圾消息反复唤醒 |
| 依赖从未就绪变为就绪 | 是 | 若整个公司暂停，仍只积存 |
| 周期职责到期且数据可用 | 是 | occurrence_key 去重和有限补跑 |
| 一般 FYI、“收到”、重复失败日志 | 否 | 下次上下文按需合并 |
| 工具仍运行但没有新信息 | 否 | supervisor 监听句柄，不模型轮询 |
| 系统核对定时器 | 否 | 普通程序检查持久待办 |
| 配额到点但状态仍未知 | 只做受限资格检查 | 不无限失败请求，不推断额度已恢复 |

### 31.3 防止“刚要睡就来活”的协议 <a id="subsection-31-3"></a>

**写入端**在一个事务中持久化工作/消息，更新接收者 work_generation，并 upsert 相应 WorkSignal/outbox。**休眠端**持有同一员工调度记录的锁，重新检查可行动待办、代次和活动会话状态，再标记 sleeping；不能“先查空，隔很久再无条件写休眠”。

若新任务先提交，休眠检查会看到它，不进入无待办睡眠；若休眠先提交，之后的新工作写入会推进 work_generation 并留下持久信号。事件通知只是缩短响应时间；即使信号送达失效，程序核对也能发现待办。

工作选择采用统一加锁顺序与幂等认领，不能为处理一次 wake 启动两个会话。通知可以合并；消费者醒来后查的是全部已准入相关工作，而不是只看触发它的一条消息。

### 31.4 PostgreSQL 通知与扫描 <a id="subsection-31-4"></a>

LISTEN 连接建立后先提交订阅，再在新事务核对待办；重连后同样执行。NOTIFY 只携带非敏感提示 ID，不承载员工正文。PostgreSQL 连接结束会清除监听，通知本身不是持久订阅消息队列，因此必须有数据库待办兜底。[N03](../ARCHITECTURE.md#ref-n03)

通知器使用独立短操作；失败不会撤销已经持久化的任务。定期扫描有上界、索引和退避，默认不逐员工建立付费心跳。示例 `reconcile_interval=30s` 只是设计 fixture，G0 根据事件延迟目标与负载调节；运行资格应写清楚在“DB 可用、队列无饥饿、容量许可”下的唤醒时延目标，不承诺任意负载下即时执行。

### 31.5 持久暂停高于所有普通唤醒 <a id="subsection-31-5"></a>

Company/Mission 被手动暂停、授权过期、预算不足时，事件照常保存，员工不得因 NOTIFY 自动恢复。恢复要重验当前权限、期限、任务版本和外部数据。积压量超过配额时拒绝/合并新非必要采集，并向用户说明；不能无限吞下整月原始全文。

依赖循环检测、队列年龄和周期检查由程序执行。睡眠不是停机，waiting_peer 不是故障；若所有员工等待一个无人拥有的事项，转成明确 blocker，不让大家一起永眠。
