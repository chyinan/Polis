### 45.8 C-FEEDBACK：来自外界的新工作 <a id="subsection-45-8"></a>

#### 45.8.1 首个真实来源选择与执行边界 <a id="subsection-45-8-1"></a>

本版选择**GitHub Issues 只读轮询**作为首个真实反馈适配目标，复用已授权 HTTP/平台能力，由普通程序调度；不默认扫描用户个人全部仓库，不依赖人工复制每条反馈。安装时选择确切 repository ID/范围、只读凭据、观察起点、筛选政策和预算；没有实际配置时只运行模拟来源或界面手动反馈，不称已接通 GitHub。

collector初读issue标题/正文/状态与指定范围更新；正式triage/修复前再读取单issue的有界评论上下文，保留评论ID/revision、覆盖时间与截断。GitHub提供单issue评论的只读及分页接口。[D01](../ARCHITECTURE.md#ref-d01) 超限/无权时可以观察或等待整理，不据旧正文高置信度实施；评论正文中的命令不变成授权。完整timeline、所有webhook、远端关单/评论/发布关联不默认支持。Issues接口可能返回PR，仍按本profile识别排除。[W06](../ARCHITECTURE.md#ref-w06)

#### 45.8.2 幂等输入与有界覆盖 <a id="subsection-45-8-2"></a>

`FeedbackSourceBinding` 保存来源身份、权限/过滤 revision、采集游标和 coverage；`FeedbackObservation` 保存 provider item ID、源更新时间、原文指纹、抓取时间及模式。更新同一反馈产生新观察版本，不反复创建同名新任务；有新相关信息时定向唤醒，只有“仍然 open”不每日唤醒一次。

分清首次基线、完整扫描与增量轮询。使用分页时，页面记录落盘后才能推进该页扫描状态；只有完成本批必要页，才推进可声明的覆盖水位。限流、失联或页失败显示 `partial/stale`，不把失败页当空列表；按官方分页链接和限流提示有界退避。[W07–W08](../ARCHITECTURE.md#ref-w07)

`updated_at` 不是唯一 ID 或全局提交顺序。参考实现采用重叠时间窗口和 item ID + 内容指纹去重；必要时周期性有界完整核对。分页过程中列表可能变化，不能宣称快照式无遗漏；明确最终一致覆盖、上次完整扫描和未知删除/权限丢失。不得把 403/404 自动当作用户删除了所有 issue，也不得将不再匹配筛选的记录默认为“问题已解决”。

首版只对选定规模、在限额内可反复扫描的仓库声明资格；无法在轮询窗口覆盖时缩小范围或延长 SLA 并经用户确认，不悄悄丢最后几页。API 请求的 304/ETag 可作优化，但不能替代每页输入记录和覆盖账本。

#### 45.8.3 观察、待办与使命的关系 <a id="subsection-45-8-3"></a>

来源文字先按不可信资料保存，再规则去重/分类。准备正式接手时先按额度取必要评论；未覆盖范围明确partial，评论编辑/更正触发受影响工作核对，不靠标题匹配排除关键信息。无意义重复不调用模型，必要语义判断创建有界triage Task交现有岗位。程序限制请求/正文/评论量，不让外部工单洪峰无限烧钱。

新反馈在**有效维护/运营使命**中，符合范围才创建或更新正式任务。一次性交付已关闭后，新反馈进入 Company backlog：可以在有单独有限授权的 collection policy 下采集，但不能沿旧使命授权自动启动模型。没有独立采集授权就停止轮询。一个公司仍只占用一个未释放使命。

对外评论、变更状态、提交 PR 属于另外的外部写 Action；首版只读 collector 不拥有这些权限。内部记录“已处理”不得说成远端工单已经关闭。后续需要反馈写回时，另登记目标与幂等/结果核对政策。

#### 45.8.4 保留真实运营指标 <a id="subsection-45-8-4"></a>

反馈来源的 completeness、时延、权限状态与业务质量分开。模型认为修好了，只能指向实际 artifact/evidence；来源后来关闭不一定由本团队修复，必须记录归因边界。公司 backlog 数、有效任务数、已验证修复与用户认可分开，不用“看到 10 条 issue”伪装“解决 10 个问题”。
