## 34. C-RETRY：重试归属、问题预算与收尾保障

### 34.1 分层，但不能倍乘失控 <a id="subsection-34-1"></a>

| 层 | 所有者 | 允许重试的内容 | 禁止事项 |
|---|---|---|---|
| DB 事务 | Repository/事务协调 | 死锁/序列化失败，重试完整纯 DB 事务 | 事务闭包里包含 LLM、HTTP 或进程启动 |
| 传输 | WorkerAdapter | 明确可重试且安全的连接/请求恢复 | 结果未知仍当未执行；新建幂等键 |
| Attempt | Scheduler | 工具或模型失败后有限再次尝试 | 对权限撤销、人工暂停、额度耗尽空转重试 |
| 策略 | 固定规划岗位 | 在使命授权内改变路线 | 换任务 ID 洗掉历史次数和成本 |

底层 SDK/harness 隐藏的重试必须探测并尽量关闭或计入上界；不可见时报告 `retry_visibility=limited`。不能在无法知道总请求次数时声称精确 hard cap。

### 34.2 ProblemKey 的用途和边界 <a id="subsection-34-2"></a>

同一个缺陷、外部 Action 或已识别阻塞关联稳定 ProblemKey，父子任务沿用其问题预算。预算记录 attempt 数、策略修订数、协调消耗、已否定路线和最后有效进展。新名字不是新问题；模型请求新的 ProblemKey 也经内核的关系规则检查。

不承诺对所有自然语言“是不是同一个问题”自动完美判定。结构不明时依然有 Mission/Employee/Provider 总预算作为外层硬边界；可疑重复进入去重/升级流程，而不是无限创建无限预算。

### 34.3 保护验收与恢复，但不创造额外额度 <a id="subsection-34-3"></a>

每个 Mission 可配置 `closing_reserve`，包含验证、接班、在途核对需要的额度。普通工作准入必须满足总可用余额减去未占用保护额度之后仍足够；被授权的 closing 类任务可使用这部分，但仍不能越过 Group/Company/Provider 上限。

保护额度不是重复扣账的已花费用，也不是一次消费再在多个层级相加。分类由固定任务模板/政策决定，不能任意开发任务自称 recovery 使用保留金。若必须恢复的模型也没额度，程序先安全停下，保存最小交接包；不能冒用其他公司资源。

容量同样保护：即使开发槽满了，也应为工具停止、核对和验收留出普通程序处理能力。推理槽与网络连接池不能将急停管理路径完全堵住。

### 34.4 何时稳定停止 <a id="subsection-34-4"></a>

已达无进展/重试/费用边界时，产生 `blocked_no_progress` 或 `ended_not_met`，附失败类别、证据、下一步需要的新条件。只在新证据、新授权或不同可验证路径出现时恢复。停止后不再让模型为了“讨论停止”持续开会。

waiting_quota 只按明确返回时间/有限探测恢复；认证失效等待正常授权。消息无法送达按队列逻辑处理，不同时创建新员工来绕过失败。安全中断允许未知费用继续结算，不能在停止时清零负债。

### 34.5 默认值与真实费用 <a id="subsection-34-5"></a>

示例中的重试次数、核对间隔和保护额度是测试参数。真实运行前用户批准总预算；没有批准时 pay_enabled=false。计算实际成本包括加载上下文、审查、协调、失败、接班及工具资源；订阅配额和 API 美元费用分账，不用估算伪装真实账单。
