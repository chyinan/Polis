## 32. C-REVOKE：授权生效、撤回与派发线性化点

### 32.1 把“以前批过”与“现在可以执行”分开 <a id="subsection-32-1"></a>

Action 的历史 `authorized` 只记录曾通过政策检查。最终派发前还要验证：当前 GrantRevision、公司/使命状态、员工 epoch、输入/产物 hash、目标资源、有效期、风险规则与预算。

采用短期、单次的 DispatchPermit，绑定 action_id、attempt_id、employee_epoch、grant_revision、target_hash、input_hash、expires_at。permit 不能被另一个任务/目标复用；未到发送阶段不能把它当外部成功。

### 32.2 明确可实现的顺序保证 <a id="subsection-32-2"></a>

首版所有同作用域撤销与最后派发请求经过可信 dispatcher 的序列化门禁；许可消费记录在受控数据库事务中提交。**许可被最终消费进入发送管线**是本项目的派发线性化点。撤销生效后不得产生新的有效消费；已在此点之前进入发送管线的操作，属于在途集合，必须列出。

不能在数据库和任意远程 HTTP 之间制造不存在的原子性。许可已提交但还未写出网络、发送后回执丢失、远端已经处理但本地未记录，都可能跨越故障窗口。能确认尚未发送时取消；不能确认则保守进入 outcome_unknown。不得以此承诺“按按钮返回之后绝不可能看见任何外部效果”。

门禁只覆盖经过本项目受控 dispatcher 的路径；原生 shell 绕过出口的能力必须由执行隔离解决。不存在靠一句 RPC 检查就能约束所有网络包的承诺。

### 32.3 管理 API 的三个状态 <a id="subsection-32-3"></a>

| 状态 | 用户可以相信什么 | 不能推断什么 |
|---|---|---|
| revocation_accepted | 请求已持久化，开始建立屏障 | 工具或发布已经停止 |
| effective_for_new_dispatch | 后续动作不能拿到/消费有效许可 | 已在途动作一定不再产生效果 |
| quiesced | 受影响执行已停止或隔离，所有在途项已核对或被明确保留为隔离的未知项 | 过去已经发生的业务效果被撤销 |

对仍有不能隔离且可能继续执行的动作，保持 revoking/unknown，不显示 quiesced。核对后可报告“执行已隔离，但外部结果仍未知”，不能把未知改成失败。

### 32.4 竞态处理 <a id="subsection-32-4"></a>

撤销先于最终许可消费：拒绝动作，并结算可确认尚未消耗的预留。许可消费先于撤销：登记在途项，尝试有能力的取消/隔离与核对。许可检查后输入版本变更：最终门禁拒绝旧版本。恢复进程重启：先恢复撤销屏障和在途记录，再允许调度。

幂等键在同一业务意图重试中保持稳定；副作用未知时不发新键。补偿、撤回、更正、退款是新的有权限要求的动作，不因为“恢复”就获得无限授权。

### 32.5 对话不授予管理权 <a id="subsection-32-5"></a>

人类在聊天里说“先停一下”可以由 UI 生成待确认的管理动作，或在明确约定的已认证控制交互中执行；来源仍必须是人类管理身份。其他员工转发这句话、网页出现类似文字或模型总结里的建议，都不能成为撤销/批准管理事件。

紧急隔离不需要 LLM 协商；控制面 DB 不可用时停止新的许可消费，UI 标记存储不可用，而不是借用内存旧授权继续冒险。
