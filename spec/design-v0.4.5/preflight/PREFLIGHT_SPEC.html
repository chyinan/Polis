42. 开工收口：启动、员工操作、信任、接班一致性与 QQ 接管通知

42.1 本次范围与证据等级

本章补齐从“公司已配置”到“开始工作、持续交接、正确结束、确需人时发出通知”的接缝。不新增动态岗位，不更换 Go/PostgreSQL/React 基线，不恢复办公室场景，也不把 QQ 变成另一个 Agent 控制台。

本版新增明确需求：首版纳入 QQ Bot 作为接管通知通道；只对需要人采取行动的异常进行外发，不向 QQ 转播员工日常聊天。 通知由确定性程序和模板生成，不调用模型，不依赖 Kokoro 应用同时运行。

本轮经 GitHub 连接器核对 Kokoro-Engine 的 src-tauri/src/qqbot/{config,protocol,runtime}.rs。该实现使用 QQ 官方 AppID/AppSecret、Access Token、OpenID 与 C2C/群聊 API，而不是 OneBot/NapCat。P01–P03 用户报告既有实践成功；本次只检查源码片段及协议，不重新运行 Kokoro，也没有连接或发送任何 QQ 消息。

修正：Kokoro 所读路径是被动回复，但 QQ 官方 API 接入生态已经有主动发送实现。 腾讯插件源码与 Hermes 通知配置提供了额外的一手依据。Q01–Q03 本版明确采用主动路径，不依赖近期入站消息；G0 只补齐我方应用/目标/消息形式与无人看守窗口的资格证据。官方细则未完整取得，不写死旧配额，也不改用非官方 QQ 协议。

下述合同和样本均为 accepted-for-implementation / not_run。静态 schema 合格只证明设计样本满足结构，不证明模型、数据库竞态、QQ 服务或隔离已经通过。

42.2 C-MISSION：唯一启动、使命占用与收尾

42.2.1 从启动命令到第一份工作

保存公司和Mission草案不执行模型。StartMission核对管理身份、当前版本、基础Agent读/规划环境、使命授权、预算与资源；项目依赖尚未ready不阻止获准的bootstrap/环境准备。按任务类型准入，见12.1/46.6。通过检查后在一个短事务内：

  1. 锁定公司使命占用记录并核对当前 MissionRevision；已由同一使命占用则返回对应启动状态，不重建组织。
  2. 建立持久 MissionActivation，保存稳定 activation_id 与命令回执。首版不重开已终结使命；继续同一未终结使命使用 resume，另一个长期目标新建 Mission。
  3. 创建唯一的 bootstrap_plan 任务，约束为 (mission_id, activation_id, bootstrap_kind) 唯一；重复键或不同 request_id 的重复启动仍不得创建第二份。
  4. 负责人来自人确认的现有规划岗位。输出合同来自受版本管理的 BootstrapTemplate，不依赖尚不存在的项目计划。
  5. 写入 WorkSignal/outbox、公司流事件和运行阶段 phase=bootstrap 后提交；只有提交成功才按现有规则进行付费执行准入。

BootstrapTemplate 至少要求输出：近期里程碑、可执行任务、负责人、依赖、可检查验收安排、关键假设与待确认歧义。任务本身有时间/费用上限；无合格规划员工时返回有理由的阻塞，不自动聘用替身。初始规划可以创建后续验证工作，但不能自行改写人批准的成功标准或授予新权限。

计划接受只证明结构和授权有效，不证明路线一定正确；领域质量检查与独立验收仍按第 13、30 章执行。只有确实阻止推进的重要歧义才形成 HumanIntervention；不要求人提前手写全部子任务。

创建组织（无推理）→ 明确启动使命
                    → 事务性唯一 bootstrap 工作
                    → 唤醒固定规划员 → PlanProposal
                    → 结构/授权/资源检查 → 现有员工并行工作

42.2.2 “一个活跃使命”不是只检查 active 枚举

新增 CompanyMissionSlot，记录尚未释放的使命占用。active、waiting、paused、evaluating、closing 等未终结生命周期都占槽；额度等待和人工暂停不能被当作可启动第二使命的理由。phase=bootstrap 是执行阶段，不增加另一套公司状态真相。

首版同公司一次只有一个未释放使命。计划修改是版本修订，不是重建 activation。重复 start 对已启动使命只返回现状或明确冲突；对已终结使命拒绝重新启动，防止旧消息和旧授权被复活。

42.2.3 收尾分离业务关闭与历史账务核对

在成功候选、明确失败、到期或取消后进入 closing，记录拟议 terminal_reason。关闭流程必须先阻止新业务任务、周期实例及旧工作线唤醒，再处理在途事项：

项目 收尾要求
周期职责与待执行任务 停止产生新 occurrence；已有实例明确取消、过期或保留，不静默删除
员工承诺 逐项以已履行、明确取消或有授权的移交闭合；“取消”不能记为“验收通过”
写工作区和外部操作 排空、停止或有效隔离；不能用关闭状态掩盖仍能写入的旧执行
产物和证据 固定版本、保留必要 pin，发布带缺失项的报告；未知项不能填成通过
费用与迟到回执 允许程序继续对旧 Action/Attempt 结算，归属旧使命，不唤醒旧业务

业务执行权已收回、受影响资源已安全交接、未决责任有明确处理后，才设置终态并释放使命槽。未结算费用本身不必永久占槽，但继续占用父级预算的 unknown liability；不能释放同一个仍可能被旧动作修改的外部资源。不能确认隔离的动作阻止相关资源释放并产生接管事项。

MissionSucceeded 只能在既定验收满足时产生；不能把 cancelled、ended_not_met 或无法核对的效果改名为 succeeded。终态历史不可被迟到消息直接重开；所有后续任务必须属于新的有效使命。

42.3 C-EMPLOYEE-OPS：员工如何使用组织，而非只让组织管理会话

42.3.1 固定员工有独立生命周期

每个固定 Employee 由运行时管理独立 Session/Attempt。规划员不是所有员工必需依附的父会话；规划员掉线不删除其他成员。底层 harness 原生 subagent 不是新 Employee，默认禁用未受管理的递归 delegation；确需启用时按第 14、20、29 章单独认证并计费。

定义小型、版本化 employee-ops@1 工具合同。可由适配器映射到经过资格测试的动态工具/MCP 等入口，内部语义保持一致；不为接一个后端再建立第二份任务真相。未经验证的工具接入标为 unverified，不用 TUI 敲键或自然语言猜测冒充稳定协议。

42.3.2 首版最小操作集

操作 允许输入 确定性结果与权限限制

workspace.list/search/read/snapshot 授权根、文件/范围/版本，快照限当前拥有者 明确文件发现与快照；细则见 44.3/44.7；读取不等于写或自动共享

42.3.3 身份、幂等、错误与大小

实际 actor、company、employee、session、attempt、epoch、授权能力来自运行时签发的会话绑定。worker 提交的上下文 ID 只作为交叉核对和定位，不能用于自授身份。restoring 与 active 使用不同 grant 类别。

写操作带 request_id、idempotency_key、expected_revision、协议版本；相同键且不同正文返回冲突。工具结果至少区分 persisted、operation_pending、rejected、outcome_unknown，并提供 receipt/operation ID。服务端返回 STALE_EPOCH、REVISION_CONFLICT、OUT_OF_SCOPE、INPUT_TOO_LARGE、POLICY_DENIED、MALFORMED_INPUT 等稳定错误码，而不是让下一层解析中文错误句子。

事件正文、单次检索、日志片段和重试均有可配置上限。格式错误允许受预算约束的修正；不能把提交失败解释为完成。任务/工具/进程真实观察由程序增量落盘；模型不写日报也不能使已知回执丢失。服务端游标只确认扫描进度，不冒充员工已读；work.checkpoint 不能删掉未闭合 Obligation。恢复只读会话仅可使用授权读取和 handover.confirm，以上新的写操作均不可用。

42.3.4 接入边界

Codex app-server 继续是第一后端；员工协议绑定须在固定版本上验证注册、调用、事件、重复请求与恢复。第二条真实路径必须报告是“同 harness 换模型”还是“跨 harness/供应商接班”。只完成前者不得声称后者通过。

普通 QQ 通知不向任何员工公开 notify.send 或 QQ 凭据。员工只能提出有证据的阻塞请求，由运行时判断是否转化为需要人处理的通知。

42.4 C-BOOTSTRAP：首次管理员、凭据与持续授权

42.4.1 单人本机建立信任，不抢占网页管理员

首版由宿主受信 OS 用户执行拟议 orgctl init-owner，走只对该管理身份开放的本机初始化入口。初始化凭据随机生成、一次性、短期有效，服务端只保存验证摘要；不通过 URL、公共日志或 worker 环境传播。管理员在此流程建立持续登录凭据，浏览器获得受控会话。初始化后关掉 bootstrap 入口；无默认 admin/admin，也不允许未初始化 Web 页由首个访问者抢注。

具体密码摘要与会话实现采用经审阅的成熟密码库，不自创算法；精确参数、过期时间、速率限制、CSRF 和安全 Cookie 在 G0-IDENTITY 固定并测试。文档样本不包含真实初始化码或密钥。

本机管理入口与 worker 工具入口分权限；本地 loopback 不是身份凭据。首版远程管理只复用明确配置、认证且可达的部署入口，不自动开公网端口或创建隧道。

42.4.2 三种生命周期分开

对象 失效后的影响
浏览器登录会话 无法继续查看/管理；不自动撤销已经批准的使命
Mission AutonomyEnvelope 到期或撤回后不允许新的业务派发；按撤权屏障处理在途项
员工执行凭据/供应商凭据 对应执行暂停或换班；不改变公司的目标与其他人的授权

退出工作台或浏览器过期不停止公司；人明确撤回使命则不能用员工 token 仍有效作借口继续执行。更换管理员登录凭据默认撤销旧浏览器会话，是否暂停使命使用单独明确选项，不混入隐式行为。

42.4.3 SecretRef 必须有真实的安全读取路径

首版服务凭据从受信控制进程可读的宿主凭据文件/服务凭据入口读取，文件与父目录使用严格权限并与 worker OS/容器边界隔离；供应商认证仍沿合法原生路径，不提取订阅 token 自建代理。文件权限不是磁盘加密，也不防已控制宿主管理员的攻击者。 不将全部父进程环境原样继承到 worker。

SecretRef 只存绑定信息，不存真实秘密。Kokoro 的环境变量命名可作为配置映射参考；不能直接把它允许的明文 app_secret 字段复制进版本化公司配置或接班包。P01

重启后凭据可以安全读取才允许自动接续；若部署采用人工解锁而尚未解锁，进入 waiting_secret_unlock。无凭据时不从日志、旧导出或其他公司寻找“备用钥匙”。整公司备份不包含明文凭据，恢复前重新绑定。

QQ Bot 接收目标与其所属主体也由管理路径绑定；知道某个人的 OpenID 不是管理员身份认证，更不授予该人任意公司权限。

42.5 C-RESOURCE：实际资源归属与行动粒度

42.5.1 配置别名不是资源身份

引入 ResourceBinding 与规范化 ResourceKey：记录 provider/environment、实际外部 ID、目标对象、读写类别与公司授权。仓库优先使用平台仓库 ID + 目标 ref；本地目录同时核对已批准根目录与运行时实际文件边界；内容发布使用平台、应用和实际账号上下文。不能仅按用户填的 URL/别名判断隔离。

同仓库的 HTTPS/SSH 别名或两个公司指向同一个共享分支，必须识别或阻止歧义写入。无法证明两个别名是否同一目标时不宣称独占保护；保守要求人确认映射并在执行前复核。

首版对共享分支、部署目标、发布账号等需独占业务写入的资源只允许一个当前所有者。冲突拒绝，不立即实现跨公司谈判。只读共享可另授；模型 provider 账号是受共享容量/预算管理的资源，不等于要独占整个账号。QQ 通知 bot 也可由多公司共用一个受控发送器，但每个接收目的地的可披露公司范围单独授权，不让员工直接使用该账号。

独立 clone/工作区内的并行开发仍可进行；严管的是共同受影响目标。租约过期不证明旧工具停止；ResourceKey 所有权转交必须连同旧写者隔离证据和资源 epoch。

42.5.2 三档动作边界

类别 示例 首版治理方式
只读观察 读取已授权文件、取执行状态 会话权限/查询大小/来源规则；不因此调用模型
受限环境内本地工作 编辑隔离 clone、在无凭据环境跑测试 Task/Attempt 授权 + 可验证隔离 + 观察/检查点；不每改一行都跑发布审批
共享或外部效果 更新共享分支、发布、部署、QQ 通知 受控 ActionIntent、现行授权、单次派发/核对；用途特定的权限和数据规则

QQ 通知属于控制面授权的运维外发，不是员工的业务工具；员工休眠、普通业务暂停或模型额度为零，不妨碍已授权的通知发送。人单独关闭外发/撤销通知授权则必须停止新通知；它不能借“紧急”绕过凭据和接收者范围。

42.5.3 审查不是“所有目录都不可写”

审查输入是冻结、只读的候选代码快照；编译输出、测试临时文件、缓存放独立有界 scratch。验证前后核对输入 hash，防止测试脚本修改候选后仍称原版本通过。被审代码及脚本同样不可信，验证进程不能读管理凭据或突破网络/文件限制。

固定 Reviewer 若提出测试补丁，将其作为独立候选变更；不能修改生产候选、随后以同一员工身份批准修改后的结果。需要时交其他独立验证入口或有权人决定，不自动创造新岗位。

42.6 C-CONTINUITY：一致接班快照、只读恢复与产物发布

42.6.1 事实与游标使用同一短快照

接班包、需快照水位的工作台读取，使用同一短 REPEATABLE READ 事务取得相关数据库事实、有效版本与公司提交有序 company_seq。Read Committed 连续语句可读到不同已提交状态，不能把旧任务内容和较新游标拼成一个包。P05

BEGIN ISOLATION LEVEL REPEATABLE READ READ ONLY;
-- 在统一公司作用域下读取任务、责任、动作、引用和 company_stream_head。
-- 将结果复制为不可变的事实清单，不在事务中调用模型或读取大型文件。

之后在事务外装配摘要与文件；生成包记录应用生成的 snapshot ID、游标、引用版本、缺失项和内容 hash；snapshot ID 是来源标签，不是事务结束后还能重用的数据库快照句柄。对包构建后的新增事件可靠补齐。激活前重新核对当前授权、关键依赖与恢复代际；一致快照不是永久有效授权。

对文件 GC 使用有期限的 MaterializationLease/保留 pin：取得事实清单前建立有界的防删除保护，取到明确引用后转为精确 pin，再释放宽范围保护。长时间构建需续约；保护已失效或引用缺失时停止发布并重新核对，不假定旧快照文件还存在。具体实现不能在 GC 扫描与新增引用之间无锁竞态，也不能让废弃构建永久占磁盘。

42.6.2 恢复核对阶段没有业务写权限

restoring / validating 使用专用 read-only grant：只能读取接班包、冻结产物和必要证据，并发送接班声明。必要的验证工具仅在独立 scratch 使用受控配额运行；不能修改业务工作区、发新协作任务、消费发布许可或扩大授权。

通过核对后，内核原子提交新 employee_epoch 与 Session/Attempt 的激活决定，但先显示 activation_pending_environment，不立即派发任务。受信 supervisor 按当前 incarnation/epoch/grant 幂等落实写能力，返回可核对的 capability receipt；内核确认回执仍对应最新授权后才显示 active 和放行工作。

DB 与挂载/OS 授权不是一个原子事务。能力落实失败或回执丢失时保持 pending 并核对，不回滚到已退役 epoch；迟到的旧授权请求由 supervisor 的当前代次/冻结门禁拒绝。写能力落实与撤权也走同一监督门禁，不能让排队的旧 mount/grant 在撤权之后重新生效。旧写者未停止/隔离时不进入此流程；受信 supervisor 不可达则停住，不让 DB 状态冒充 OS 隔离证据。

激活前到来的消息由版本/游标补齐；激活后按正常收件箱继续。handover.confirm 只是新模型的声明，程序还要核对可检查的 ID、来源、epoch、责任和产物。 能力清单还包含工作根、SkillRevision 和 MCPBinding/工具描述指纹；恢复只读阶段不执行脚本或写工具，实际环境落实后才可使用。详见第 44.6 节。

42.6.3 产物发布：允许孤立文件，不允许半成品变成证据 

创建 staging 记录 → 受限临时写入 → 完成并计算内容指纹
    → 文件 Sync/必要目录持久化 → 同文件系统固定不可变路径
    → 持久化检查成功 → DB 将 ArtifactRevision 标 ready 并写事件

文件持久化和 rename 语义要按受支持的 OS/文件系统实测，不能把 rename 当作所有断电场景下绝对可靠。固定路径不对不可信执行者开放覆盖；公司命名空间隔离，不用跨公司去重泄漏内容相等性。

崩溃在 DB 发布前可留下孤立文件，启动核对后回收或认领；DB 引用缺失/损坏文件则标记 missing/corrupt 并使受影响验收失效，不能继续绿色通过。不要从“传输成功”或“文件名存在”推出内容完整。

待提交文件可能包含半写入修改。接班只能使用已完成快照或明确标识为待修复的工作区状态，不能包装成完整可运行产物。GC 同时检查活跃任务、未完成责任、接班包和备份 pin。

42.7 C-NOTIFY：真正需要人时的 QQ Bot 接管通知

42.7.1 首版交付内容与明确不做的事情

首版实现一个通用 NotificationChannel 端口和 qq_official 适配器；默认优先绑定管理员 C2C 目标，群目标只有人明确确认披露范围后启用。它是确定性告警传输，不是 LLM 岗位，不参与任务规划，也不依赖 Kokoro Engine 启动。

参考 Kokoro 的协议拆分、token 生命周期、OpenID 白名单、状态/错误分类；按 Go 实现一个最小通知适配器。不照搬聊天消息进入 AIOrchestrator 的链路，不带 Tauri、角色记忆、语音、多媒体或整个 Bot 平台。Kokoro 的会话/消息内存去重也不能替代本系统的持久事件与通知投递记录。P01–P03

首版仅管理后台配置 + 受控外发。不接受 QQ 文本命令进行批准、充值、续期、运行 shell、恢复使命或解除阻塞；不根据“收到/继续/同意”推断管理员已授新权。需要 QQ 接收事件来完成特定资格/绑定时，也仅在受审核适配中处理，不进入模型；通用 QQ 对话与远程管理命令延期。

42.7.2 触发规则：异常不等于需要打扰老板

HumanIntervention 来自可检查事实和政策判定，可由员工提出但不能直接外发。记录 severity、reason_code、affected_scope、ProblemKey、已尝试恢复、保护动作、需要人的具体行动、期限、证据引用和状态版本。

普通任务完成、员工休眠、同事 ACK、正常等待依赖 仅工作台/日志，不推 QQ
短暂网络故障或工具失败，正在额度与次数内自动恢复 不立即通知；恢复成功只留记录

42.7.3 三套状态分开：问题、投递、管理决定

记录 状态示意 不能代表什么
HumanIntervention open → acknowledged → resolved / obsolete acknowledged 仅表示人已在工作台确认看到，不授权业务
NotificationDelivery pending → sending → provider_accepted / retry_wait / rejected / outcome_unknown / exhausted / superseded 平台接受不等于用户收到或阅读，更不等于问题解决
管理命令/审批 请求 → 受理 → 应用/拒绝/未知 QQ 消息或点击详情链接不能直接替代此流程

人未响应时，受阻工作保持安全等待；与该问题无关且仍在授权范围的工作可继续。不加钱、不放宽验收、不把 QQ 回复当批准。浏览器确认已知可停止同级提醒；升级风险仍按预授权规则生成新通知。问题解决或过期后，不再发送排队的旧接管通知。

42.7.4 持久 outbox、去重、节流与有界重试

在创建/更新 HumanIntervention 的事务中写通知意图，daemon 在事务外转交唯一 sender；实际 HTTP 外发仍在事务外。逻辑去重键包含作用域、ProblemKey、incident_occurrence、接收路线、严重性档位和提醒代次。同一未解决发生期复用 Incident；有证据的恢复之后再次故障生成新的发生期，不能被旧去重记录永久压掉。相同故障的一百条日志合并成一个问题，不唤醒一百次发送；不同公司正文不能互相合并进未授权接收目标。

发送前重新核对：问题仍需人处理、当前 route_revision/目标仍有效、敏感度与披露范围允许、平台资格未过期、通知 TTL 未过、限流与重试预算允许。正文从当前合法状态生成，关键通知版本与 hash 必须记录。禁用、解绑、问题解决或撤销披露授权后，未跨最终派发门禁的旧消息失去资格；已进入发送管线的清单与冻结回执按 42.7.8 核对，不能保证撤回已在途消息。

提醒次数和间隔由人确认的通知政策设置；示例值只是 fixture。通道/接收目标级限流独立于模型配额。发送只花普通网络/平台资源，不调用模型，不借用员工的付费推理槽；可能的平台费用或其他成本仍按实际口径记录。

远端没有可靠幂等/查询保证时，不宣称 exactly-once。明确被拒绝按错误分类处理；回执丢失进入 outcome_unknown。纯提示消息在人预先接受少量重复的策略下可有限重试，始终带相同 incident ID 方便识别；不能将该策略泛化到发布、退款等业务动作。默认不开无限提醒，不通过换新通知 ID 重置限额。

QQ 不可用时，问题继续保存在工作台。已达通知重试限额后标 channel_degraded，停止递归“通知发送失败再通知自己”；恢复后只发送仍有效的汇总/当前问题，过时积压标 superseded。

42.7.5 QQ 主动通知：实现路线已确认，账号资格另外验证

首版正式实现 QQ 官方 Bot 的主动接管通知；它不是“有近期入站消息才顺便回复”的方案。 腾讯维护的 tencent-connect/openclaw-qqbot 明确提供定时主动推送；本次定向读取的 src/features/proactive.ts 在主动路径调用发送函数而不带入站 msgId。Hermes 官方文档也以 QQBOT_HOME_CHANNEL 指定 cron/通知 OpenID。Q01–Q03

这确认的是有来源的实现路线，不是本项目已完成实现，也不是所有 Bot/目标/消息类型都享有无限发送权。腾讯的使用说明同时提到主动消息可能被 QQ 侧拦截。Q01 G0-NOTIFY 要验证实际应用和无人看守情境的资格与可达性，而不是重新证明“有没有主动发送这种架构”。

层级 当前结论 实现与验收要求
上游机制 upstream_source_confirmed：有不绑定入站消息的主动发送路径 保留来源、读取范围与版本指纹；不等于我方适配器已实现
本项目适配器 not_implemented Go 最小实现；不移植聊天/语音/批量广播/QQ 审批逻辑
实际 route unverified：尚未提供账号或发送 按 app/environment、目标类型、OpenID、消息格式单独验证
无人看守覆盖 not_run 即时测试外，测试长期无对话、进程重启、token 刷新、平台拒绝和限流

优先验证管理员 C2C 的短文本通知。群通知是独立资格，C2C 通过不能给群通知自动打勾；频道、语音、文件、图片、交互按钮不在首轮范围。消息格式从已验证的最小文本形式起步，链接可选；不能在一次超时后盲目改用另一种格式重发。文本形式也被平台拒绝时，记录失败，不伪装投递成功。

Kokoro 已核对的 AppID/AppSecret、token 生命周期、OpenID 白名单和协议拆分可继续借鉴。P01–P03 它当前所读的 build_text_reply_body / send_text_reply 是带 msg_id 的被动回复路径；这不代表 QQ 平台只能被动回复，也不影响采用已确认的主动路径。三份项目资料分别记录，不能将任一项目的上线效果当成本项目实验结果。

发送使用明确的 (provider, app_id, environment, target_kind, target_openid)，不按字符串外形猜 C2C/群，不把 QQ 号码当 OpenID。换 AppID、环境、目标或影响发送的凭据/权限配置必须使资格失效，重新绑定与核验；一次常规 token 刷新不等于更换账号。已知用户列表只帮助定位目标，不自动授予敏感通知的接收权，不导入“广播给所有已知用户”的行为。

QQChannelQualification 至少记录：

  • token 获取/刷新，精确应用/环境与非秘密配置指纹；
  • 主动/被动、C2C/群、文本/链接各自的资格状态与证据；
  • 没有近期入站 msg_id 时的主动测试、无对话时间跨度、重启后结果；
  • 已知的平台错误类别、限流与可核对回执能力，不伪造未知配额；
  • 测试时间、失效条件、当时的 sender/协议配置版本及实际收件确认。

主动发送请求不伪造 msg_id，不使用保活聊天或账号轮换规避平台限制。msg_seq 或任一 SDK 参数只有在官方语义和实测成立时才可参与去重，不能被默认解释为任意重启后通用的幂等键。当前接口路径/headers/token 规则由固定 EndpointProfile 管理，员工无权修改；不向任意自定义 URL 发送 Bot 凭据。

QQ 官方消息细则页面本轮仍未完整取得；因此不写死全平台统一的条数、窗口或历史政策日期。Q04 route 未通过时，界面显示“主动通知路线已选定；本应用未验证/受限”，而非“平台不支持主动发送”。可以继续受监护开发，不能将它列为已认证的无人看守告警保证。

42.7.6 传输回执不是本地生成一个 ID 就算成功

本地 NotificationIntent/Delivery ID 与平台 message_id 分开存。平台无 message_id 时不得随机生成一个值冒充远端回执；只保存实际返回的证据和 remote_message_id=null。明确成功响应可以显示 provider_accepted 并注明缺少查询句柄；响应结构无法判定时保留 outcome_unknown，而不是凭 HTTP 200 一律成功。

错误按已核对的平台 code 与 HTTP 类别联合分类：认证失效最多触发有界、并发合并的 token 更新；发送权限/目标拒绝不反复刷新 token；限流按可得的重试提示与本地上限处理；未知响应不触发格式切换或新 ID 洗重试。原始错误文本不进入 QQ 正文或公开日志，通知只用白名单 reason_code 对应的脱敏模板。

42.7.7 通知内容、隐私与手机访问

正文使用稳定模板，默认仅包含：安装/公司安全别名、incident 短 ID、严重级别、脱敏原因、已采取保护动作、需要人做什么、发生/观测时间，以及可用的受认证工作台定位信息。原始提示词、源码、完整日志、客户名称、文件路径、额度密钥和接班包不发送到 QQ。

[需要接管] 研发一组 · INC-DEMO-01（模拟样本）

未配置可供手机访问的可信 base URL 时，不发送 localhost 链接冒充远程入口，显示编号即可。配置了经过认证、TLS 与可达性验证的管理入口后，可以附不带凭据的详情路径；访问仍需登录。没有 bearer token、审批 token、一次点击即可执行的 GET 链接。若平台不支持该链接形式，降为文本定位，不试图扩大域名/网络授权绕过。

公司名称和问题原因也可能敏感；默认使用人配置的安全别名和脱敏 reason 映射。员工提供的错误描述作为数据处理，不能直接拼进可执行 Markdown、任意链接或群 @ 指令。

42.7.8 单一物理发送器、离线基础设施告警与撤销屏障

为避免 daemon 和 watch 各自持有旧路由、分别刷新同一 Bot token、重复发送，本版将实际 QQ HTTP 外发集中到已有的独立 orgctl watch 进程内。它同时承担轻量监督和通知传输，不新增第三套调度服务；通知未启用时无需启动这一进程。daemon 仍拥有 HumanIntervention、通知政策、业务 outbox 和权威投递记录。

正常流程：daemon 在当前政策下形成脱敏通知信封，经受认证的本机 IPC 交给 sender；sender 仅接受已批准 route、消息 hash、用途、短期单次许可、当前部署代际与限流规则全部匹配的请求。不开放员工可用的通用发送接口，不信任仅来自 localhost 的请求。 Bot 凭据仅在 sender 的受信环境读取，不进入 worker。watch 不读取公司 DB 或原始工作内容；可见的是需要投递的已授权最小摘要。

业务通知不在 sender 内建立另一套长期队列：待重试工作留在 PG。sender 只保留有限传输状态和回执，用于本机故障后核对，不擅自重发历史业务信封。正常业务重试每次回到 daemon 重新检查问题是否仍存在、route 是否有效，再申请新的传输尝试，而不是新的业务意图。

DB/daemon 不可用时默认不发业务问题正文。 人可另外批准一个用途极窄的 InfrastructureNoticeCapsule：限定安装别名、固定接收者、固定不可用模板、明确失效时刻、最大发送次数和发送频率。它只允许说明“运行时/存储当前不可用，业务状态未知”，不包含公司业务、自动续期或任何控制权。capsule 默认禁用；PG 不可用时使用它属于之前明确批准的离线运维授权，不冒称查询到了最新业务政策。

撤销不能只在 PG 里改一行。统一命令依次记录撤销意图、通知 sender 冻结对应 route、持久化本机拒绝代次并返回屏障回执。只有 sender 已停止接受该旧版本，或原授权已可证实过期，才显示 effective_for_new_dispatch；无法联系 sender 时保持 revocation_pending，不得显示“所有外发已关闭”。受信本机管理入口可直接要求 sender 冻结/停止以降风险，不依赖故障的 PG；PG 恢复后记录对账。这条入口只降权，不签发新 route 或新业务授权。

sender 对最终许可消费与冻结使用同一个串行门禁，并保存状态。已经跨过最终许可消费边界的请求属于在途集合，仍可能产生消息；能确认未发则取消，不能确认则记录 unknown。已排队不等于已派发；拒绝新派发不等于撤回手机已收到的消息。 人确认问题已解决与投递交错时同样按这一边界处理，不能承诺跨数据库和远端的绝对原子性。

离线 capsule 的期限不能因墙钟回拨或进程重启自动延长：运行中使用单调经过时间和固定绝对期限的保守较早边界；时间异常或无法验证旧 capsule 时拒绝外发。首版 sender 重启后离线 capsule 默认失效，须在线重新同步；这意味着 daemon/DB 同时不可用且 sender 也重启时，不保证继续通知。不是悄悄恢复旧备份中的外发权。

离线外发前必须先持久记录本机 InfrastructureActionIntent、capsule 消耗次数及传输尝试；记录失败不外发。未知回执保留，不因重启清零次数。PG 恢复后将这些记录作为历史观察对账，不重放一次发送。基础设施事件和去重状态只在本机有界日志里保存，容量/写入失败时停止新发送并保留宿主错误信号，不建立第二份公司账本。以安装 ID、故障发生代次和恢复标记归并基础设施问题；不要用一个永久 ProblemKey 抑制第二次真实故障。sender 与外部同时运行的 Kokoro/Hermes 使用同一 AppID 的冲突行为尚待资格验证；默认建议专用 Bot 应用，或明确声明外部用量/凭据更新不可见。

同机 watch 不覆盖整机断电、全机断网、QQ 平台失效或自身同时故障。 首版不自动部署外部监控。无人看守启用前展示 coverage gaps，并要求人明确接受；覆盖整机故障的主张必须以后由外部监督及实测支撑。业务暂停不关闭已授权运维提醒；全局“停止所有外发”必须包括 sender 和离线 capsule。

42.7.9 工作台接入与配置顺序

在集团/公司设置加入“接管通知”面板，在现有待决事项页展示 Incident 与 Delivery，不新建一个聊天产品。流程为：选择 qq_official → 管理员绑定 SecretRef 和明确目标 → 选择允许外发公司/级别/安全别名 → 设置有界提醒与降级行为 → 保存禁用草案 → 明确同意发送测试 → 获得资格报告 → 单独启用通知政策。

查看设置、打开下拉框、刷新状态不发送消息，也不调用模型。测试消息也是真实外发：需显示接收对象与模拟正文，经明确操作后发送，记录单独测试回执；导入本设计包绝不触发测试。生产通知启用不等于业务使命启动，反之亦然。

界面分别展示配置已保存、资格未验证/受限、发送失败、平台接受、结果未知；没有已读回执就不显示“老板已收到”。确认接管只在已认证工作台执行，确认不自动恢复；解决问题需要新的可核验条件或正式管理命令。

42.8 本版接口与持久记录增补

新增逻辑记录包括 MissionActivation/CompanyMissionSlot、员工操作回执、初始管理员与会话绑定、ResourceBinding、MaterializationLease、HumanIntervention、NotificationRouteRevision、NotificationIntent/Delivery 与 QQChannelQualification。它们是现有 Go/PG 的模块与表组，不是要求新部署七个服务。

最小通知端口示意（不是现成 SDK）：

NotificationChannel
  InspectConfiguredRoute(route_revision) -> passive/readiness facts
  ProbeProactive(route_revision, explicit_test_authorization) -> qualification
  Send(notification, route_revision, notification_grant) -> transport_receipt
  Reconcile(receipt) -> facts / unsupported

Inspect 不发送探测消息；ProbeProactive 有单独外发授权；Send 不能调用 LLM；不支持远端核对时返回 unsupported/unknown，不构造假回执。token 缓存刷新按实际 expires_in、有界提前量和并发合并处理，不使用无证据永久有效缓存。鉴权失败和主动消息权限不足分开，不把每个 403 都当 token 过期反复刷新。

员工操作、通知配置、接班元信息、回执的 JSON Schema 在 schemas/ 统一维护，示例在 examples/；样本中的 execution_enabled/pay_enabled/send_enabled 全为 false、真实 SecretRef/收件目标为空，所有资格 unverified。它们不是可直接启动的生产配置，也不是真实 QQ API 请求体。

源码取证元数据在 evidence/kokoro-qq-source-review.json，只包含路径、blob 指纹、读取范围和结论，不包含用户凭据或复制的源码。先复用机制、独立实现受控边界；后续直接采用代码时另行登记许可和来源。

42.9 开工顺序、门禁与变更控制

门 现在就固定的要求 必须用运行证据补齐的部分
G0-LIFECYCLE 唯一 bootstrap、暂停占槽、closing 与迟到核对 并发启动、重复 start、收尾时崩溃、旧消息不复活
G0-EMPLOYEE employee-ops@1、受认证身份、原生子代理不等于员工 真实工具注册、模型调用、过期 epoch/幂等/大输入
G0-IDENTITY 本机管理员初始化、三种授权生命周期、SecretRef 实际读取 初始化滥用、登录/登出/撤权、重启解锁、worker 隔离
G0-RESOURCE 规范化实际资源、独占写目标、验证 scratch 别名冲突、旧写者、路径边界、候选 hash 不变
G0-CONTINUITY 同快照事实+游标、只读接班、文件先固定后发布 真实 PG 并发、各崩溃窗口、GC/接班竞态
G0-NOTIFY QQ 官方、接管才发、确定性模板、无 QQ 管理命令 已确认主动路径的实际 C2C/群资格、限流/鉴权/重启、冻结屏障与离线授权

适用的程序路径先用 fake worker/模拟 sender 检查，再以真实 PG 和获授权后端验证；不能把模拟结果写成 QQ 已打通。0.4.1 的计划全部保留，本版额外增加 FT-71～82、NT-15～22、UI-29～32；所有产品测试仍为 not_run。

未通过主动 QQ 资格时，允许继续开发与受监护实验，但不能将其标为可用的无人看守告警通道。真正长跑前还要人确认实验总预算、数据保留、实际部署与通知覆盖范围。文档不自动取得这些授权。

本轮收口的终点：从人启动使命，到员工按正式工具协作、断线接班、产物验收，再到必要时发出一次可追溯的 QQ 接管提醒，整个过程都能解释“谁、依据哪个版本、做了什么、哪些仍未知”。 此后优先运行小闭环，让证据驱动修订，不继续无边界增加设想。
