# R0.5B9 deterministic delivery transaction

## Current implementation boundary

The product worker now exposes `polis_task_submit` as the explicit final-delivery decision. Its public input is exactly `{}`: the call is the Agent's decision, while Task/session/epoch, TaskValidationBinding, workspace digest/revision and validation receipt are derived from the trusted worker context. `polis_artifact_submit` remains available only to historical/non-product registries and is not in the current product surface.

The current delivery flow is:

```text
workspace_replace → workspace_check PASS → task_submit
  → durable artifact_staging intent + CAS blob
  → one TXWrite publication transaction
       → qualified checkpoint
       → Artifact + task_validation_artifact_qualifications
       → Task candidate
```

The checkpoint is generated by `NewQualifiedProductDeliveryCheckpoint` and stores the current PASS receipt, binding digest, workspace digest/revision, session/epoch, runner revision, qualification state and policy revisions. The checkpoint remains a real `worker_checkpoints` row and is the provenance for the Artifact qualification row.

## Responsibility matrix

| Concern | Owner | Notes |
| --- | --- | --- |
| Understand Task and edit workspace | Agent | `workspace_replace` remains explicit and CAS-protected. |
| React to validation feedback | Agent | `workspace_check` still returns PASS/FAIL and receipt feedback. |
| Decide to deliver | Agent | Calling `task_submit` is required; PASS never auto-publishes. |
| Task/session/epoch/employee binding | Control plane | Trusted `Binding`, `TXWrite` guard and current Task row. |
| Validation binding and current PASS receipt | Control plane | Rechecked inside staging and final publication transactions. |
| Workspace digest/revision | Control plane | Current `worker_workspaces` row; stale or changed state fails closed. |
| Qualified checkpoint fields | Control plane | Deterministically derived; Agent no longer echoes them. |
| Artifact/CAS/staging/publication | Control plane | Uses existing staging/CAS architecture and product qualification relation. |
| Candidate transition and post-publication fence | Control plane | Same final transaction; existing candidate fences remain. |

## Public failure classes

Product delivery policy failures use structured `PeerToolRejection` data. The implementation distinguishes `validation_required`, `validation_not_passed`, `validation_receipt_invalid`, `validation_receipt_stale`, `workspace_changed_since_validation`, `writer_fenced`, `task_state_disallows_delivery`, `delivery_already_committed`, `artifact_staging_failed` and `artifact_publication_failed`. Business preconditions use policy/ conflict codes; staging/publication infrastructure uses an explicit phase and retry guidance.

## Recovery and duplicate semantics

This is not a distributed exactly-once claim. `artifact_staging` and the content-addressed blob are durable prerequisites; the checkpoint, Artifact, qualification relation and candidate transition are one database transaction under the company lifecycle lock. A failure before final commit leaves no final checkpoint/Artifact/candidate state and a retry resumes from the durable staging/CAS boundary. A response-uncertain failure after commit is recovered by the same `TXWrite` receipt key or by the unique task qualification row. Replays for the same validated Task/workspace return the existing Artifact and never create a second checkpoint or Artifact.

Fault coverage in the R0.5B9 disposable PostgreSQL harness covers after staging intent, after CAS publish, after checkpoint insert, after Artifact qualification insert, after Task transition and after commit/response uncertainty.
