## Backend/API boundary

- `cmd/polis serve` starts the read-only Workbench HTTP server.
- `internal/workbench` owns the typed product DTO, read-only PostgreSQL projection, scoped HTTP routing, cursor validation, and event presentation adapter.
- The store requires a dedicated `polis_r0_` database at schema 5 and uses `RepeatableRead` + `ReadOnly` transactions.
- Product JSON uses the existing frontend View DTO casing (`companySeq`, `nextCursor`); the R0.3A peer pagination contract remains a separate business contract and is not reinterpreted by the Workbench UI.
- Invalid company/cursor/limit inputs are rejected at HTTP and read-store boundaries. Raw SQL rows, recovery internals, protocol evidence, and `evidence/development` are not exposed to React.

## Fixtures and live state

- `FixtureWorkbenchApi` remains available only for explicit `VITE_WORKBENCH_MODE=fixture` tests/demo.
- Production/default mode is `RealWorkbenchApi`; real API errors do not fall back to fixtures.
- `VITE_WORKBENCH_LIVE_UPDATES=sse` is opt-in. The current backend returns an explicit `501 live activity stream is deferred`; the frontend displays the existing closed/stale boundary rather than pretending polling is realtime.
