# R1 service readiness probe foundation

Date: 2026-09-25

## Immutable service definition

`ProjectEnvironmentPolicyManifest` optionally carries up to eight `ProjectServiceDefinition` entries. Each entry pins a stable ID, a contained `.js`/`.cjs`/`.mjs` script path, and one `ServiceProbeSpec`; it stores no caller-supplied argv. Canonicalization rejects duplicate IDs, duplicate loopback endpoint tuples, unsafe script paths, and invalid probe contracts, then sorts services by ID before hashing the policy. Policies with no services omit the field, preserving existing R1/R2 environment digests.

Workbench read validation and the environment revision panel accept and display the pinned service script and health response digest. Path validation uses UTF-8 byte length and rejects C0/C1 control characters to match Go canonicalization. This gives administrators a reviewable config in the approved environment revision; it does not launch a service.

## Probe contract

`internal/environment.ProbeServiceEndpoint` evaluates one explicitly configured health response. The target must be a literal `127.0.0.1` or `::1` address and a fixed port. The probe sends one GET to an absolute, traversal-free path using HTTP with proxying, compression and keep-alive disabled. Redirects are never followed. The service must return the configured 2xx status and exact response-body SHA-256.

The contract caps each request at five seconds, limits response bodies to 64 KiB, caps lease duration at ten minutes, and rejects non-loopback hosts, encoded/control-character paths, malformed digests, and invalid status/timeout values. The response body is not returned or logged. Both a listener-owner verifier and an established-connection-owner verifier are mandatory. Before sending any HTTP bytes, the connection verifier must bind the client's ephemeral tuple to the server-side PID for that exact established TCP connection; the listener owner is also checked before and after the probe. An open local port by itself cannot pass.

## Append-only endpoint ledger

`Kernel.TXRecordServiceEndpointEvent` persists a service endpoint observation only when its source revision, literal loopback endpoint and healthcheck digest match the immutable environment policy and its latest approval event still approves the same digest. It locks the environment revision also locked by policy decisions, so a concurrent revoke serializes with readiness updates. The caller must run `ProbeServiceEndpoint` with the process-owner verifier before submitting the observation; the Kernel writer does not inspect operating-system process ownership. Probe timestamps must be strictly newer than the latest observation. Generation starts at one; a later generation is accepted only after the prior one is revoked. Non-revoked observations must carry a lease that exactly matches the pinned duration from the probe timestamp. RequestID replay returns the same receipt, and the endpoint event plus active JobRun readiness change commit in one transaction. The generic JobRun event command may preserve service readiness but cannot promote a service to ready; that requires the endpoint writer. Revocation is terminal for a generation. The Workbench projects expired/revoked endpoints and endpoints whose JobRun is terminal as unhealthy, even before a Control cleanup worker appends the revocation event.

`StartProjectJob` accepts `kind=service` only with a pinned `serviceId`; service callers cannot supply a script or argv. Control re-reads the immutable environment snapshot, requires an executor-provided `ServiceEndpointOwnerVerifier`, launches the fixed policy script, and waits for the configured loopback healthcheck to report ready. Its monitor writes bounded leases, renews them at a fraction of their duration, records owner-verified unhealthy HTTP responses, and requests process stop on owner loss or rejected evidence. Stop, timeout, process exit and shutdown revoke a recorded endpoint; the Workbench also projects terminal JobRuns and endpoints whose latest environment policy is revoked as unhealthy. Generic JobRun events remain unable to promote readiness. The Windows Node executor confirms the PID belongs to one of its tracked, live AppContainer processes and checks the exact IPv4/IPv6 listener using `GetExtendedTcpTable`; the Windows executor verifies both listener and established-connection ownership. Linux Node/Node service Jobs remain denied pending a namespace-aware verifier and browser route.

The Workbench exposes start controls only for service IDs in a qualified, prepared Windows environment revision, sending no command or args. Disposable PostgreSQL Control integration uses a fake process owner and local HTTP fixture; a native Windows test uses local IPv4 and IPv6 TCP listeners. The real executor path, actual prepared project service, independent browser check, WFP interaction and clean-VM qualification remain unverified. No WFP rule, loopback exemption, real model, QQ, MCP endpoint or external service was used.

## Slice 38 review hardening

Schema 32 persists `JobRun.ServiceID`; request fingerprints bind the selected service even when two definitions share one script path. The Workbench start receipt and history expose that ID. Existing service rows are labeled `legacy:unattributed` because their selection cannot be reconstructed safely from the historical endpoint tuple; the colon form cannot be used as a new policy service ID. Endpoint writes now require the persisted JobRun service ID, policy service ID, loopback tuple and healthcheck digest to match.

Revocation stores one immutable in-memory RequestID and probe timestamp until the append-only write is confirmed, so an ambiguous commit can replay the same event. If a process stop was initially unconfirmed but a later wait proves exit, Control revokes the service endpoint and reconciles the JobRun to `cancelled`; persistence failures keep the process/job handle reachable for a later Stop retry. On restart, an unknown Windows JobRun can be explicitly stopped only after the environment profile is confirmed and the new executor has no tracked live process; the prior Windows Job Object uses kill-on-close and no job is relaunched. Windows AppContainer process exit state and process-handle closure are synchronized under the same mutex, avoiding a closed-handle reuse race.

The Windows owner verifier checks IPv4 and IPv6 listener tables, requires an exact loopback row owned by the tracked process, rejects wildcard and competing rows (including IPv4-mapped wildcard rows), and rejects IPv6 wildcard listeners that might accept IPv4 dual-stack traffic. Immediately after `DialContext` completes, it checks `TCP_TABLE_OWNER_PID_ALL` for exactly one server-side established row matching the service address/port and the client's ephemeral address/port, and requires that row's PID to match the tracked AppContainer process. The HTTP transport receives the socket only after that check, so a different same-port process never receives the health request. Microsoft documents that `SO_REUSEADDR` can force multiple same-port binds with indeterminate packet delivery, including same-account binds; this connection-specific owner check closes that transient listener-spoofing gap ([Winsock address reuse guidance](https://learn.microsoft.com/en-us/windows/win32/winsock/using-so-reuseaddr-and-so-exclusiveaddruse), [GetExtendedTcpTable](https://learn.microsoft.com/en-us/windows/win32/api/iphlpapi/nf-iphlpapi-getextendedtcptable), [MIB_TCPROW_OWNER_PID](https://learn.microsoft.com/en-us/windows/win32/api/tcpmib/ns-tcpmib-mib_tcprow_owner_pid)). Each bounded table call and the probe's final readiness transition recheck cancellation/deadline. R1 remains unqualified pending complete AppContainer/browser/clean-VM qualification. The Workbench projects policy revocation as unhealthy immediately; process stop is observed by the lease monitor within one bounded probe interval plus the bounded request/stop operation.

Schema 33 adds a stronger endpoint lease nullability constraint without rewriting immutable legacy endpoint rows. Workbench readback omits a lease timestamp for revoked rows, including malformed historical rows accepted before this constraint.

Review follow-up: neither `HasExited` nor a cleared root-process handle alone proves the descendant tree is stopped. Windows Stop and restart reconciliation now wait for the AppContainer monitor's completion, which closes the Job Object before publishing completion. Historical `legacy:unattributed` service rows display their identity but hide the policy-bound revocation action. Full native Windows runner and Control test binaries pass; Linux-only Control fixtures skip on Windows. Actual project AppContainer service execution, WFP, browser and clean-VM qualification remain open.
