# R2 GitHub Issues read-only adapter foundation

> Updated: 2026-09-29, Slice 74 / Schema 53. The fixed-profile collector, manual company backlog, and default-off scheduled collection path have offline and disposable-database evidence. Live GitHub qualifications remain absent.

## Adapter contract

`internal/feedback/github` reads one explicitly bound repository using only GET requests. The production base is fixed to `https://api.github.com`; a token is obtained through an injected source that receives the selected repository ID/owner/name and is never returned in results or error text. Before scanning, the adapter confirms the repository numeric ID and full name, then queries Issues using an overlap-window `since` filter, `state=all`, and `sort=updated` ascending.

The client follows GitHub `Link` pagination only when the next URL remains on the same API host and same repository-ID path, advances exactly one page, and preserves the frozen filters. Pull requests are excluded using the issue response `pull_request` field. Repeated observations are deduplicated by issue ID, with the newest update retained. Before comments are read, the repository and issue ID are checked again and pull requests are rejected.

Issue and comment body sizes, page response sizes, page counts, item counts and comment context are bounded. Page response SHA-256 and ETag, item update times, original body hashes, and truncation flags are returned. 401/403/404, rate limits, malformed responses, unsafe pagination targets, network errors and limit exhaustion have safe reason codes. The client returns partial coverage without `CoveredThrough` when a scan is incomplete; it does not retry automatically.

## Verification and official API notes

Local `httptest` cases cover exact repository ID verification, two-page collection, PR exclusion, overlap dedupe, page/host/filter validation, incomplete-page watermark protection, issue/comment bounds, body fingerprints, permission failure and primary/secondary rate-limit classification. No GitHub account or external API request was used.

The adapter follows GitHub's documented `Link` pagination and maximum `per_page=100`. The Issues endpoint can return pull requests, identified by `pull_request`. Fine-grained repository access requires Issues read for issue listing; comments need Issues read or Pull requests read. See [Issues REST endpoints](https://docs.github.com/en/rest/issues/issues), [Issue comment REST endpoints](https://docs.github.com/en/rest/issues/comments), [REST pagination](https://docs.github.com/en/rest/using-the-rest-api/using-pagination-in-the-rest-api), and [REST rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api).

## Remaining integration

Schema 24 persists immutable `FeedbackSourceBinding`, permission/approval events, scan/page evidence, and append-only issue revisions. Schema 25 adds immutable comment scan/page/comment observations tied to the exact stored issue revision. The Kernel refuses scans until the selected repository has a verified read probe and a separate human approval. `LatestGitHubFeedbackCursor` returns only the `covered_through` of a complete issue scan; partial scans may append issue observations but never advance that cursor. A dedicated PostgreSQL test covers the approval gate, durable page/issue/comment links, overlap revision append, immutability and complete-versus-partial cursor behavior.

The company-scoped Workbench `GET /feedback` projection now reads source permission/approval/coverage state and bounded issue/comment revisions from PostgreSQL. UTF-8 output limits are enforced by the SQL projection and rechecked by the React DTO validator. The Feedback page renders this text as untrusted read-only content and exposes explicit source registration, read-only permission probing, human approval/pause/revocation and one-shot poll actions. Probe and poll require a deliberate button press; ordinary page load only reads stored observations.

Control now exposes explicit source registration, permission probe, manual decision and one-shot poll commands under the authenticated Workbench API. Polling refuses sources that are not approved and permission-verified before calling the provider. A single poll is bounded to a 90-second context, three issue pages/300 items, and comment reads for at most five most-recent issues with one page/100 comments each. It reads through the fixed-host GET-only client, persists complete/partial evidence through the Kernel, and uses an injected token source; `cmd/polis` does not configure one, so external reads remain disabled by default. Replaying a completed poll request ID returns stored scan/comment coverage without another provider call.

Windows has a current-user DPAPI credential store under the Polis secure profile. Linux now has a `secret-tool` adapter for the current user's D-Bus Secret Service keyring; it is available only when `secret-tool` and `DBUS_SESSION_BUS_ADDRESS` exist. It passes the token over stdin (never argv), uses a 5-second command deadline, limits lookup output, filters child environment variables, and redacts keyring errors. Both stores expose the same fixed `default-readonly` reference. `cmd/polis` injects the protected token source only when `POLIS_GITHUB_READONLY_ENABLED=1`; storing a token alone does not enable or issue a GitHub request. Windows DPAPI store/read/rotation/delete tests passed in a native Windows test binary with a fake token. Linux adapter tests use an injected mock command runner; they did not contact a D-Bus Secret Service. See [go-keyring Secret Service notes](https://github.com/zalando/go-keyring) for the Linux Secret Service/D-Bus integration contract.

Schema 51 adds an append-only `feedback_backlog_events` ledger. A complete or partial persisted GitHub scan adds new issue revisions to the company backlog as `open`; owner actions can change only internal status and require the exact latest revision plus a rationale for local handling reasons. Stale decisions conflict. A newly observed issue revision re-enters `needs_review`, while the provider's current `RemoteState` remains separately visible. The Workbench exposes an explicit internal-status control, and its receipt states that the remote issue was unchanged. Dedicated disposable PostgreSQL coverage verifies idempotent writes, stale-revision fencing, changed-revision review routing, remote-state separation and company isolation. No backlog item automatically restarts a mission, creates a Task or invokes a model.

Schema 52 adds an append-only per-company/source collection policy history, schedule state and reserved poll attempts. Schema 53 adds an atomic dispatch claim: it validates the Kernel advisory lease/runtime incarnation, locks the active Company and exact source/attempt, then rechecks current policy and permission state, and marks `started` before an external GET can occur. A policy disable, source revocation or company archive that commits before that claim prevents the request. Only an already started poll can expire as `outcome_unknown`; a reservation that expires before dispatch is recorded as failed with a known no-send reason. Expired-attempt cleanup commits before company locks to keep lock order consistent. Same-slot replay remains blocked. Only an approved source with a verified read permission can enable a policy; cadence is fixed within 900–86,400 seconds. The scheduler remains dormant unless both `POLIS_GITHUB_READONLY_ENABLED=1` and `POLIS_GITHUB_FEEDBACK_SCHEDULER_ENABLED=1` are set and the protected credential store is available. Each tick reserves at most three sources and reuses the fixed-host GET client and limits as manual polling. Workbench supports policy enable/disable and shows next/last attempt state. Fake-provider PostgreSQL coverage verifies default-off and explicit company-policy gates, schedule reservation, disable/revoke-before-dispatch barriers, outcome-unknown after a started lease expires, no same-slot replay and no Task creation. No external GitHub request was made.

Tokenless desktop mode now requires the session token for every company feedback read and write route.
