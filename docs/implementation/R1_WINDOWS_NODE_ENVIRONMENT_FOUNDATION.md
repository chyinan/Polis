### Slice 70 — Fixed loopback service listener policy

The immutable service probe pins the listener to exactly `127.0.0.1` or `::1` and one TCP port. Runner grants `internetClientServer` only to a service JobRun, then installs a dynamic SID-scoped WFP policy that allows the exact address/port bind, listen and loopback TCP accept path while blocking other resource assignments, listeners, accepts and outbound connects. The dynamic lease stays owned until the exact process tree is confirmed stopped. If caller cancellation occurs, the wrapper continues with a bounded cleanup wait; unknown tree state or filter-session close failures retain the lease and block another launch. The Windows isolation fingerprint is now `windows-appcontainer-node-policy@5`, and the owner qualification report must include `windows_service_listener_network_boundary`. Windows filter creation now sets and pins the API-required `FWPM_FILTER0.DisplayData.Name`; registry-only install rules receive the same fix.

Pure plan and lifecycle tests pass on Linux; the Windows Runner test binary cross-compiles. Native mock-only WFP builder/lease tests and process-lease lifecycle tests pass using synthetic SID pointers. No system WFP filter, `CheckNetIsolation`, loopback configuration, Node/npm project, or service JobRun ran. The service listener/browser path and effective WFP behavior still need independent isolated-host qualification. ### Slice 69 — Ready-service browser gateway

After the existing fixed health probe has persisted a ready lease, Workbench can create a company/job-scoped browser session. The URL carries a single-use five-minute ticket; the bootstrap response sets an ingress-specific HttpOnly/SameSite=Strict cookie and performs a same-origin navigation to the service root. A random per-ingress cookie name prevents collisions across browser ports and upstream cookies with that reserved name are discarded. Host traffic reaches only the pinned service address/port; the proxy checks listener and connection ownership, limits requests and responses to 8 MiB, limits concurrency and total request duration, rejects Fetch Metadata from cross-origin sites, checks Origin for writes, rejects upgrades/off-target redirects, and preserves non-proxy application cookies. Explicit stop and daemon shutdown close the gateway before stopping the service process; the authenticated Workbench route is token-gated even when desktop session tokens are disabled.

This gateway does not create AppContainer listen permission, install WFP or loopback policy, launch an isolated browser profile, or store rendered-page evidence in the JobRun ledger. A headless Chromium smoke against a local service fixture clicked the ticket, followed the bootstrap and rendered the app page; the page's same-origin fetch reported `Sec-Fetch-Site: same-origin`, and its final URL omitted the ticket. This fixture does not exercise the Windows AppContainer or packaged desktop. The gateway is exposed only after the host health probe can reach the service. Native AppContainer listener/network behavior and packaged browser integration remain `not_run`. Evidence: `evidence/development/r1-r3-implementation-validation-20260929-slice-69-service-browser-ingress/verification.md`.

## Implemented

- The generic Windows process launcher keeps a kill-on-close Job Object and 64-process bound for Provider Worker processes. AppContainer project Jobs use the same process-tree ownership and cleanup model plus a 50% hard CPU rate, 2 GiB per-process memory, and 2 GiB aggregate Job memory limit. Resource setup failure prevents process resume. Breakaway is not enabled. The current project isolation-policy fingerprint is `windows-appcontainer-node-policy@5`, which binds the bounded NTFS workspace and exact service-listener network policy. The Job Object limits and WFP behavior still require independent host qualification.
- `runner.NewAppContainerSandbox` creates a unique Windows AppContainer profile with an empty capability list (network deny-all), launches only an executable and working directory inside the profile's private LocalAppData tree, passes an explicit environment, redirects standard streams, and assigns the suspended process to a named per-execution kill-on-close Job Object during `CreateProcess` through `PROC_THREAD_ATTRIBUTE_JOB_LIST`. Project JobRuns use their durable JobRun ID as that execution identity. On root exit and Stop, the monitor closes the root-process handle, terminates any surviving descendants, and waits for the Job Object active-process count to reach zero before publishing cleanup or issuing `StopProof`. Cleanup uncertainty remains an error and retains the environment ownership. `ReconcileWindowsProcessTree` reopens the exact named object, verifies its process-tree policy, terminates remaining members, and waits for the same zero count; it does not rely on a PID that may have been reused. `runner.NewWindowsNodeNPMInstallAppContainerSandbox` is the separate install-only path: it creates a per-lease authenticated loopback proxy, grants `internetClient` only to that AppContainer process, installs an AppContainer-SID-scoped dynamic WFP policy for the exact loopback proxy IPv4/TCP/port, and adds only that SID to the Windows loopback list. Its launch contract accepts only the pinned `node.exe npm-cli.js ci --ignore-scripts --no-audit --no-fund --registry=...` shape; arbitrary project commands wait until registry egress has been revoked.
- The proxy admits authenticated HTTPS CONNECT requests for exact configured registry hostnames on port 443 only. It rejects IP literals, unlisted hosts, subdomains, malformed authority targets, wrong/missing credentials and non-CONNECT requests; it bounds active tunnels, queue rejections and handshake input. It resolves IPv4 A records only and pins the connection to a checked globally reachable address. IPv6 answers and DNS64-only results are rejected because no IPv6 address is requested or dialed; private registries require a separately qualified policy. Its IPv4 denylist is tied to the IANA [IPv4 Special-Purpose Address Registry](https://www.iana.org/assignments/iana-ipv4-special-registry), last updated 2025-10-09. Injected tests use an in-memory dialer and do not access a registry.
- Native Windows tests check the manually declared WFP ABI sizes/offsets and exercise an injected WFP API for filter plan, partial failure cleanup and dynamic-session close. They do **not** install a WFP filter, change the Windows loopback SID list, prove effective filter arbitration, or qualify elevation/access rights. Loopback read/modify/write is protected by a named cross-process Polis mutex and preserves all returned SID attributes; it cannot coordinate arbitrary applications that do not use the same mutex, because the Windows list API has no compare-and-swap. Heap-release failure after a successful Set is tracked as committed and triggers rollback. The WFP path is therefore implemented but remains unqualified on a real Windows policy state.
- `environment.PrepareWindowsNodeNPMInstallSnapshot` validates the frozen project plan and separately selected Node/npm source-file digest before opening a registry-only AppContainer, then stages project files separately from an exclusive `.polis-toolchain` directory. It verifies the canonical `windows-node-toolchain@1` digest. Windows read-only file-sharing leases deny write/delete while the Node image and npm CLI are in use; handles stay open until all tracked process trees stop and the snapshot closes. `LaunchNPMInstall` is the only snapshot method that can launch with registry egress and derives argv from the pinned plan (`npm ci --ignore-scripts --no-audit --no-fund --registry=...`); generic project launch rejects while the permit exists and uses deny-all after revocation. Every later snapshot launch rechecks the staged toolchain digest. `RevokeRegistryEgress` deletes only the WFP permit filter while keeping both default-block filters; a revoke request blocks new launches immediately, including when filter deletion fails, and failed cleanup remains retryable.
- `Control.EnsureProjectEnvironment` now re-reads the verified MissionInput CAS snapshot, records `starting`/`running`, invokes an injected executor only after the kernel reports `accepted`, and stores bounded redacted preparation output and evidence in CAS before the terminal event. Missing executor configuration records `blocked_unqualified`; non-qualified policy paths never invoke the executor. Request replay and concurrent ensure calls cannot relaunch a starting or terminal run. PostgreSQL JSONB policy verification canonicalizes the stored value and compares its digest, so database whitespace/key ordering does not cause a false integrity failure. Stale accepted/starting/running/ready records are invalidated on startup; normal shutdown invalidates in-memory prepared profiles before cleanup.
- `cmd/polis serve` leaves the Windows executor disabled by default. Enabling it requires `POLIS_WINDOWS_NODE_PREPARATION_ENABLED=1`, administrator-selected `POLIS_WINDOWS_NODE_PATH` and `POLIS_WINDOWS_NPM_CLI_PATH`, and `POLIS_WINDOWS_NODE_WORKSPACE_ROOT`. The latter must be a direct child of a pre-provisioned NTFS volume labeled `POLIS_WORKSPACE`, 1–16 GiB, with free space and a distinct identity from the control and Windows system volumes. The volume should be dedicated to Polis workspaces; its logical capacity is a hard aggregate ceiling shared by all AppContainers, not a per-job quota. The bundle digest must match the immutable environment revision. Runner creates a unique directory per AppContainer and applies a protected DACL granting the package SID controlled workspace access and the control user/SYSTEM/Administrators cleanup access. Project material, staged toolchain, and the explicit HOME/LOCALAPPDATA/TEMP/TMP paths use this root. The executor runs only fixed `npm ci --ignore-scripts --no-audit --no-fund` inside the registry-only AppContainer, redacts proxy credentials from output, revokes the permit, then retains the deny-all snapshot for the current service lifetime. The same executor is the only `ProjectJobExecutor`. JobRun start requires the persisted policy/executor gates, a `compat` Task in `working`, its matching active WorkerSession, and a ready memory-resident snapshot. Only bounded `.js`/`.cjs`/`.mjs` batch scripts are enabled; service and controlled-input Jobs remain blocked pending their contracts.
- Schema 19 JobRun rows/events now drive `POST /tasks/{task}/jobs`, `POST /jobs/{job}/stop`, task-scoped status listing, and `GET /jobs/{job}/logs`. Logs are a bounded redacted JSON manifest stored in company CAS and the immutable event stores its digest and stream offsets. Process-tree stop requires the snapshot's AppContainer identity and PID proof. Startup marks accepted/starting/running Jobs `outcome_unknown`; it never replays a process side effect. Service close cancels and drains active JobRuns before invalidating the memory-only environment. Service health probes and independent browser verification remain open.
- Preparation admission is bounded to two active runs plus eight waiting requests. Control passes a verified snapshot-loader callback, so queued requests do not hold immutable source bytes. Queue overflow reports `environment_executor_busy`. On an unconfirmed stop, output pipes are aborted and process/snapshot cleanup ownership remains until exit. The Windows isolation path remains unqualified: no production Node/npm bundle was staged, no npm/project script ran, no WFP filter was installed, and no Windows loopback setting changed. WFP requires rights to add filters ([WFP access control](https://learn.microsoft.com/en-us/windows/win32/fwp/access-control)); loopback changes use a system-wide SID list that callers must preserve ([loopback configuration](https://learn.microsoft.com/en-us/windows/win32/api/netfw/nf-netfw-networkisolationsetappcontainerconfig)).
- The launch sequence follows Microsoft's documented [AppContainer process creation flow](https://learn.microsoft.com/en-us/windows/win32/secauthz/implementing-an-appcontainer); its file/network boundaries are described in [AppContainer isolation](https://learn.microsoft.com/en-us/windows/win32/secauthz/appcontainer-isolation).
- `internal/environment` defines the `windows-node-npm@1` metadata gate. It accepts bounded `package.json` and npm lockfile v2/v3, checks the root dependency declarations match, rejects project `.npmrc`, npm shrinkwrap, workspace/link entries and unapproved/non-HTTPS tarball sources, and returns fixed `npm ci --ignore-scripts --no-audit --no-fund` argv for trusted absolute Node/npm paths.
- The project plan stores package/lockfile hashes and can revalidate them before preparation. This slice adds an AppContainer-backed `LaunchNodeProjectScript` primitive, but no project script was executed.
- `MaterializeNodeNPMProjectFiles` now copies a validated immutable snapshot into a newly created child of an application-managed root. It rejects traversal and Windows device names, symlinked roots/parents, existing workspaces and stale metadata; files are created exclusively and their hashes are rechecked after writing. This helper does not execute the project and is not yet connected to an AppContainer-qualified preparation runner.
- Schema 19 persists immutable project environment revisions, policy decisions, executor qualification events, idempotent preparation runs and append-only state/log metadata. Migration 48 distinguishes executor, host, isolation-policy and Node toolchain fingerprints; the token-authenticated owner command binds a qualification/revocation to verified same-company CAS check evidence. Kernel and Control commands register versions, approve/revoke a digest-pinned policy and request preparation. Requests stay `blocked_policy` or `blocked_unqualified` unless both gates are satisfied. A prepared AppContainer is retained only in memory for this service lifetime; persistence/restoration and invalidating a stale `ready` record after shutdown remain open.
- Schema 19 also persists immutable JobRun specs and append-only state/log-offset and service endpoint/readiness events. Schema 20 requires active service endpoints to have a lease. Kernel job creation requires an approved policy, a matching executor qualification and a ready environment. Workbench exposes read APIs; the task jobs page shows environment gates, JobRun states, service readiness, offsets and truncation/gap flags.
- Delivery package unit and dedicated PostgreSQL/CAS integration coverage checks artifact bytes, the canonical manifest, SHA-256 list and package digest. React API tests accept a valid package and reject changed ZIP bytes; desktop auth tests cover the manifest/download token-gate predicate. Browser UI plus desktop session middleware has not been exercised together.

### Slice 49 — host-confirmed Windows JobRun reconciliation (2026-09-27)

The AppContainer project JobRun identity is now the persisted JobRun ID rather than the prepared workspace ID. A named Job Object is assigned by the process-creation attribute before the suspended process thread resumes. On normal root exit and Stop, the tracked process now closes the root handle, terminates remaining members and waits for active-process count zero before publishing cleanup or `StopProof`. A timed-out cleanup remains `outcome_unknown`; retry can use an identity-bound host proof to release retained environment ownership only after the named Job Object is empty or absent. After a controller restart, `ReconcileUnrestoredProjectJob` opens that exact Job Object, checks its containment limits, terminates any remaining tree members and waits for the same zero count. If the object no longer exists, its kill-on-close lifetime proves the tree has exited. Open/query/termination uncertainty keeps the JobRun `outcome_unknown`.

`PROC_THREAD_ATTRIBUTE_JOB_LIST` requires Windows 10 version 1703 or later (Windows Server 2016 version 1709 or later); older hosts fail closed during process setup. See Microsoft's [UpdateProcThreadAttribute reference](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-updateprocthreadattribute) and [Job Objects reference](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects).

Synthetic process tests also verify that tree-cleanup uncertainty cannot produce `StopProof`. Linux runner/environment/control package tests and Windows amd64 runner/environment/control test-binary cross-compiles pass. The native tests did not launch AppContainer, Node/npm, a project script or an external service; no WFP filter or loopback setting was changed.
