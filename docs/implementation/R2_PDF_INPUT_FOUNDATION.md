# R2 PDF input foundation

> Updated: 2026-10-29, Slice 339. Bounded PDF text extraction and a strict subset of embedded-image input are implemented locally; complete page rasterization and the R2 format profile remain open and unqualified.

Direct `.pdf` uploads are stored as a deterministic `pdf_snapshot` gzip/tar package. The package contains the original PDF, a versioned extraction record, and extracted UTF-8 text when available. Its outer CAS digest binds all three; the internal directory manifest hashes each file. Revalidation rebuilds the package from the preserved PDF and requires byte-for-byte canonical equality.

The pinned parser is `github.com/giraffesyo/pdf@v0.7.0`. Intake limits the PDF source to 6 MiB, parses at most 40 pages sequentially, caps each decoded stream at 1 MiB, caps page operators/glyphs/forms/images, limits processing time, and stores at most 16 KiB of extracted text. Parser warning codes, page coverage, image-bearing pages, truncation, original SHA-256, extracted-text SHA-256, and parser version are stored in `pdf/extraction.json`. Parser errors are mapped to safe reason codes; uploaded document text is not echoed in errors.

Slice 265 added a bounded visual input for supported embedded PDF image objects. Slice 267 makes this path fail closed on incomplete data: it checks unpacked sample byte length using per-row padding before decoding, rejects stencil (`ImageMask`) images, and accepts only exact-length unpacked samples and `DCTDecode`. CCITT, JBIG2, JPX, and other filtered codecs are omitted until their completeness behavior is verified. It decodes at most eight objects per document, with a 1,000,000-pixel ceiling per object, a 256 KiB encoded PNG ceiling per object, and a 960 KiB total PNG ceiling. An `ImageCount` larger than the parser's returned image array marks the representation truncated and adds an omission warning. The canonical `pdf_snapshot` stores PNG bytes and extraction-record entries binding page number, parser image-array ordinal, pixel dimensions, image digest, page boxes, rotation, and four page-space placement points. The ordinal is one-based within this parser's page image array; it is not an original PDF object ID. Task context attaches selected PNGs as typed image inputs, and the immutable delivery receipt includes their page number, dimensions, path, and digest. The original PDF remains an explicit `representation_not_supported` exclusion.

These are intrinsic embedded-image objects, not complete page rasters or claims of restored visible appearance. The pinned parser does not expose or apply soft masks/transparency, color-key masks, or rendering intent, so the visible PDF appearance may differ. The representation does not composite vector text, page background, or multiple objects into a single page image; pages made from vector outlines and PDFs without a supported embedded image still have no visual input. Unsupported or over-budget images are recorded as omitted, and scanned pages receive no invented text or OCR. Slice332 advances new parser records to `polis-pdf-extraction@4` and records `fullPageRenderingStatus=unsupported`, a bounded-renderer reason, and an omission warning. No page is represented as rasterized. Canonical verification continues to accept historical `@1`, `@2`, and `@3` snapshots byte-for-byte; historical @1/@2 image objects remain excluded from new active delivery, while @3 intrinsic embedded-image input remains supported. The frontend names the PDF limit and extraction boundary.

No full-page renderer is included in the current Go runtime dependency set. Adding one remains blocked until renderer dependency/license, process/runtime compatibility, page pixel/output caps, and visual-fidelity/omission semantics are selected and validated. Until then, the explicit `unsupported` record is the contract; do not synthesize a page image by placing only embedded objects on a blank canvas.

## Slice 337 renderer candidate review

No renderer was selected. `github.com/gen2brain/go-fitz` is marked AGPL-3.0 in its upstream repository. `github.com/klippa-app/go-pdfium@v1.21.4` offers a pure-Go Wazero backend and declares Go 1.26 language syntax, but its `toolchain 1.27.1` directive differs from Polis's pinned 1.26.8 toolchain and requires build integration verification. It embeds a 5,828,543-byte PDFium WASM module built from the separate `jerbob92/pdfium-binaries` `wasm-standalone` branch. The consuming module has an MIT `LICENSE` and its README describes PDFium as Apache-2.0, but the exact embedded artifact's complete third-party notices were not verified. The binary fork reports no GitHub SPDX license metadata and its source tree did not expose a consolidated notice file. This is an evidence gap, not a legal conclusion.

The go-pdfium v1.21.4 README documents a 32-bit WASM ceiling (less than 2 GiB for one bitmap and up to 4 GiB for the module), and the versioned `webassembly.go` mounts the host root/volume by default unless the caller supplies an explicit `FSConfig`. The API allows a custom Wazero runtime configuration, but Polis has not implemented or tested an empty filesystem, lower memory/time caps, output limits, one-render lifecycle, or a deterministic fidelity/omission record. The native backend additionally requires CGO and a platform PDFium install. These candidate facts do not justify replacing the current fail-closed `unsupported` status.

## Slice 338 in-house renderer feasibility

Polis consumes only the public `github.com/giraffesyo/pdf@v0.7.0` extraction API via `pdf.ExtractPages` in `internal/intake/pdf_snapshot.go`. Its public `Page` projection contains `Glyphs`, `Images`, `ImageCount`, page boxes, rotation, annotations and warnings; it does not contain drawing operators, the graphics-state stack, clipping paths or a display list. The dependency parses content operators internally through unexported types/functions, and its `internal/object` package cannot be imported by Polis.

Consequently, drawing a blank canvas with extracted glyphs and intrinsic images would omit vector paths, font glyph shapes/metrics, clipping, masks and compositing. That output cannot be labeled a complete page. A truthful self-built renderer requires a maintained parser extension/fork that exports a bounded typed drawing IR, followed by an implementation that either supports every operator encountered on a page or marks that page unsupported/partial. No such IR or subset renderer was added in this slice; @4 remains unchanged.

Source references: [pinned parser v0.7.0](https://github.com/giraffesyo/pdf/tree/v0.7.0), [public Page/Glyph API](https://github.com/giraffesyo/pdf/blob/v0.7.0/extract.go), [page image semantics](https://github.com/giraffesyo/pdf/blob/v0.7.0/image.go). ## Slice 339 bounded parser operator audit

The exact v0.7.0 source is now maintained under `third_party/giraffesyo-pdf` via a root `go.mod` replacement. An opt-in parser option reports sorted unique operator names found in page/Form/annotation appearance streams, capped at 256 names of 128 bytes each. Structural, stream, work-limit, malformed, or audit-budget failures set `ContentOperatorNamesComplete=false`. The audit does not expose operands or graphics state, is not a display list, and does not qualify any operation as rendered. It is disabled by default, so PDF @4 snapshot bytes and historical verification remain unchanged. Fork tests run with `scripts/test-pdf-parser-fork.sh`; see `evidence/development/polis-self-dev-v1-go-patch-delivery-20261009-req35-parser-operator-audit-20261029/verification.md`.
