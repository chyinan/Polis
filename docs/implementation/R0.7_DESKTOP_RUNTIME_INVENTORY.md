# R0.7 Desktop Runtime Inventory

> Last verified: 2026-09-22
>
> Scope: Windows 11 Tauri v2 desktop host added on top of the existing Go/PostgreSQL/React product. This is an inventory of the repository as found before the desktop slice; it intentionally does not change the existing browser/server path.

## Current startup contract

### Frontend

- Authority: `frontend/`.
- Production build: `frontend/package.json` runs `tsc -b && vite build`, producing `frontend/dist`.
- Browser development: `npm run dev` through Vite, normally `127.0.0.1:4173`.
- Browser API base: `VITE_WORKBENCH_API_BASE_URL` or `/api/workbench`; Vite proxies `/api` to `VITE_WORKBENCH_BACKEND_URL` or `http://127.0.0.1:8080`.
- Production API client: `frontend/src/data/real-workbench-api.ts`, selected by default in `frontend/src/app/App.tsx`. The current browser client has no desktop session-token header.
- Fixture mode exists only when `VITE_WORKBENCH_MODE=fixture`; it is not a production fallback.

### Go backend

- Entry: `cmd/polis/main.go`.
- Start command: `polis serve`.
- Required environment for `serve`: `POLIS_DSN` and `POLIS_BLOB_ROOT`.
- Optional environment: `POLIS_WORKBENCH_ADDR` (current default `127.0.0.1:8080`), `POLIS_WORKER_MODE` (current default `deterministic`), and provider variables for `real` mode.
- HTTP authority: `internal/workbench/http.go` and the command service/read store behind it.
- Current process readiness is indirect: store/kernel open and worker adapter readiness must succeed before `ListenAndServe`; there is no explicit HTTP health/readiness endpoint.
- Current server logs are inherited stdout/stderr. No desktop log file, PID record, uptime record, or exit classification exists.

### PostgreSQL

- Version authority: PostgreSQL 18 in the repository's supported development tooling (`.tools/pg` and `scripts/`), with Go `pgx` and Goose migrations.
- Migration entry: `db/migrate.go`; embedded migrations are `db/migrations/00001_r0.sql` through `00011_r06_notifications.sql`.
- Database safety rule: `db.Migrate` refuses database names that do not start with `polis_r0_`.
- Existing dev scripts initialize/start a disposable cluster and use `trust` authentication for tests. Those scripts are development-only and are not a product security model.
- Current server startup assumes an already-running database. It does not initialize a cluster, create a role/database, choose a port, or restart PostgreSQL.

### CAS / product data

- `POLIS_BLOB_ROOT` is the authoritative blob/CAS root used by the kernel and read store.
- Product state is authoritative in PostgreSQL; temporary runtime/evidence files must not be used as a second authority.
- The desktop host will map `POLIS_BLOB_ROOT` to its durable app-data `cas/` directory and keep transient probes under `temp/`.

### Controlled provider runtime

- Production provider composition is in `internal/provider/` and `internal/runner/`.
- `BindCodexRuntimeConfig` loads and verifies the runtime manifest and binds executable/helper paths, semantic version, and SHA256 values before launch.
- `ProcessLaunchSpec`/native launch envelope and `ProductToolSurface()` are the existing controlled runtime/surface boundaries.
- Relevant variables for real provider mode include `POLIS_PROVIDER_TRANSPORT`, `POLIS_PROVIDER_BINARY`, `POLIS_PROVIDER_HELPER_BINARY`, `POLIS_PROVIDER_RUNTIME_MANIFEST`, `POLIS_PROVIDER_BINARY_SHA256`, `POLIS_PROVIDER_HELPER_SHA256`, `POLIS_PROVIDER_AUTH_FILE`, `POLIS_PROVIDER_ROOT`, `POLIS_PROVIDER_EVIDENCE`, and the existing exact-surface/qualification fields.
- The desktop host must not discover an arbitrary PATH executable or copy raw credentials into the React process. If the controlled manifest/auth/binaries are absent, the desktop state is setup-required/degraded; no silent download or replacement is allowed.

### Authentication and local API boundary

- Before R0.7, `serve` has no desktop-local authentication middleware and no desktop-specific CORS policy.
- Browser requests use same-origin credentials; command writes carry `X-Request-ID` but this is not an authentication token.
- R0.7 target: the desktop host creates a per-launch random token, passes it only in backend/frontend runtime configuration, requires it on product API requests, and allows only explicit local desktop/dev origins. The token is ephemeral and never persisted as product authority.

### Configuration and data directories

- Before R0.7, configuration is environment/path based and is not centralized for a packaged Windows app.
- R0.7 authoritative desktop root: `%LOCALAPPDATA%\Polis\` (resolved through Tauri's platform path API), with:

  - `config/` — non-sensitive desktop configuration and a private database credential file;
  - `data/` — durable desktop metadata/state that is not product authority;
  - `postgres/` — managed PostgreSQL cluster and its server log;
  - `cas/` — product blob/CAS root;
  - `logs/` — desktop/backend/provider diagnostic logs;
  - `runtime/` — resolved executable/runtime metadata and PID records;
  - `temp/` — startup probes and disposable password handoff files.

- Product data survives restart and upgrades. Session tokens, child process handles, readiness probes, and password handoff files are ephemeral.

## R0.7 gaps found

1. No Tauri project, package metadata, Windows installer configuration, or sidecar layout exists.
2. `polis serve` lacks explicit health/readiness and desktop session auth; it assumes a prepared PostgreSQL instance.
3. No managed PostgreSQL lifecycle, app-data layout, process ownership/job object, single-instance lock, tray, or graceful desktop quit path exists.
4. The frontend has no typed desktop IPC bridge, first-run desktop state, runtime status projection, or API-token injection.
5. Provider readiness is available as backend/provider validation logic but is not projected into a desktop startup state machine.

## Boundary decisions

- Go remains the product/domain/control/runtime authority; Rust is only the desktop lifecycle host and sidecar supervisor.
- PostgreSQL remains authoritative; no SQLite replacement or second frontend is introduced.
- Desktop business execution defaults to deterministic/fake runtime for dogfood. A real provider setup can be inspected and reported without sending real business turns.
- Auto-update, startup-with-Windows, code signing, macOS/Linux packaging, and external notification/provider business smoke remain deferred or separately unauthorized.
