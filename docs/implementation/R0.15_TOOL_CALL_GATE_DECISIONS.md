# R0.15 Tool-Call Gate — Decision Record (PLAN ONLY)

> Status: planning/decision draft (2026-11-07). **Does not authorize implementation, schema migration, process start, MCP tool calls, network/OAuth egress, Skill scripts, QQ, or provider turns.** Decisions are recommendations for a future separately authorized slice.

## Context

R0.8–R0.14 deliver a read-only capability inspection path at schema 15 (`docs/implementation/NEXT_SLICE.md`, `docs/design-plans/R0_15_MCP_TOOL_CALL_QUALIFICATION_GATE.md`). A future `tools.call` must remain deny-by-default. This record resolves the open decisions listed in the R0.15 design plan.

## D-01: Call qualification representation

**Decision (recommended):** represent call qualification as an explicit, auditable approval/receipt bound to `company_id + binding_id + definition_id/revision context + tool handle + descriptor_digest + policy_revision + authorization_ref`, stored as a dedicated persisted record when durability/idempotency/audit require it (schema 16 draft). Do **not** treat `mcp_server_definitions.qualification.probeStatus=passed` or R0.14 cached descriptors as call authorization.

**Rationale:** A passed probe proves limited discovery (`initialize`/`tools/list`, `toolsCalled=0` in the receipt contract) under the probe's conditions; it does not prove call-time safety, argument handling, egress policy, operator consent, or effect bounds. A separate record makes authorization scope, revocation, expiry (if any), and digest binding explicit and reviewable. Mutating the probe receipt to mean "callable" would blur read-only evidence with execution authorization.

**Implementation note:** the record should be revocable/disable-able and checked on every call; descriptor digest mismatch after re-probe/re-import invalidates qualification until re-approved.

## D-02: Schema 16 trigger

**Decision (recommended):** prepare a schema 16 **draft** (`docs/implementation/R0.15_SCHEMA16_MCP_TOOL_CALL_DRAFT.sql`, not placed in `db/migrations/` as an active migration) for call qualification and call receipts if the implementation needs: (1) durable idempotency across process restart, (2) auditable authorization/qualification state, (3) bounded call outcome receipts. If an implementation slice can prove equivalent guarantees with existing receipts/tables and explicit non-goals, schema 16 may be deferred; that requires a documented decision update.

**Rationale:** R0.8–R0.14 reached schema 15 without call execution. Call execution adds authorization and effect/unknown-outcome concerns that benefit from explicit persisted boundaries. Keeping the draft outside `db/migrations/` prevents accidental auto-application.

**Guardrail:** no migration is applied by this planning work. Any active migration file creation, numbering, and `migrateVersion` gate change belongs to the separately authorized implementation slice.

## D-03: MCP transport scope

**Decision (recommended):** **stdio-first**, matching R0.10's local probe path and the lowest-friction controlled boundary. Streamable HTTP/remote endpoints, OAuth-bearing transports, and hosted MCP servers are **out of scope** for the first `tools.call` implementation slice and require separate qualification (network policy, SSRF/redirect controls, TLS/auth/secret handling, endpoint allowlists, cost/egress authorization).

**Rationale:** R0.10 recorded that the local probe process was not network-sandboxed; expanding to remote transports before the local stdio call gate is qualified would widen risk. Stdio allows command allowlisting, bounded env, process lifecycle control, and local fixture MCP servers for deterministic tests.

## D-04: Effect classification and authorization strength

**Decision (recommended):** classify tool effects conservatively. The call gate must record declared/observed metadata when available (e.g., read-only/idempotent hints from descriptor annotations/probe metadata) but must **not** trust remote metadata as sufficient authorization. Default policy for first slice: treat calls as potentially effectful unless a reviewed, separately qualified policy explicitly allows a narrower class; effectful/stateful/externally visible calls require explicit operator authorization reference and stronger audit. Unknown-outcome calls (timeout/process loss/ambiguous transport) must not be reported as success.

**Rationale:** MCP tool metadata can be incomplete or incorrect; Polis must enforce authority locally (ARCHITECTURE 44.5.4). Conservative classification prevents "readOnly hint => auto-approved egress".

## D-05: Relation to product/provider tool surfaces

**Decision (recommended):** keep **employee capability MCP `tools.call`** separate from existing product/provider tool registries and from Codex employee-ops surfaces. Do not route MCP calls through product worker tool execution paths, and do not expose capability `tools.call` to provider-visible business registries without an explicit, reviewed design decision. Reuse only low-level primitives where they do not import authorization semantics (e.g., JSON/schema helpers, receipt patterns) and keep policy boundaries explicit.

**Rationale:** R0.5B product surfaces have their own qualification/fingerprinting and authorization history. Conflating them with operator-configured MCP capabilities would blur audit scope, egress policy, and release safety.

## Open follow-ups (not decided here)

- Workbench UX: read-only surfaces remain default; any call-triggering UI requires separate explicit design/authorization and must never auto-execute from list/describe views.
