## Status vocabulary

- `COMPLETE`: current product path is usable and has targeted evidence.
- `PARTIAL`: a real slice exists, but the normal user flow is incomplete.
- `BACKEND_ONLY`: authoritative/runtime support exists without a usable product surface.
- `FRONTEND_ONLY`: presentation/client support exists without an authoritative backend path.
- `TEST_ONLY`: behavior exists only in fixtures/tests/evidence.
- `NOT_STARTED`: no usable implementation in the current production path.
- `DEFERRED`: explicitly outside this milestone.
- `NO_LONGER_RELEVANT`: the design sample does not apply to the current evolved runtime semantics.

## Cross-cutting findings

| Concern | Before | R0.6 treatment |
|---|---|---|
| Production data path | Default `RealWorkbenchApi`; fixture requires explicit `VITE_WORKBENCH_MODE=fixture`. | Preserve this default and add new capabilities to the same API abstraction. |
| Scope and ordering | Read endpoints validate company IDs; events use `company_seq`; SSE is absent server-side. | Every new read/write is company-scoped; live updates use authoritative `company_seq`, not arrival time. |
| Security | Kernel fencing/CAS/TaskValidationBinding/provider authorization are real; frontend has no DB/provider/filesystem access. | New APIs remain backend-authorized, return no credentials, and expose blob content only through task/company authorization. |
| Sensitive credentials | Provider auth is supplied through environment/runtime files and not part of read DTOs. | Settings reports only configured/missing/invalid/ready and never returns or persists secrets in plain fields. |
| Fixture boundary | Fixtures are explicit simulated data and command writes are rejected. | Local notification adapter and deterministic worker are test/dogfood infrastructure, never silently substituted in production mode. |
| Explicitly deferred | Office/3D, dynamic hiring/firing, full R1/R2/R3 design, new provider qualification and live provider smoke. | Remain deferred; R0.6 only closes supporting product surfaces needed for dogfood. |

## Audit conclusion

R0.6 is not a runtime-requalification milestone. The repository already has enough authoritative runtime and read-model foundations to build the product layer, but it does not yet meet the “normal user flow requires no SQL/CLI/probe/evidence JSON” bar. The implementation must proceed serially A→I, with each slice adding a real backend contract, the existing frontend presentation, targeted tests, and a checkpoint entry before the next slice.
