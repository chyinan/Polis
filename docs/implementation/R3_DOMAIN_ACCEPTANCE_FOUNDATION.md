# R3 domain acceptance foundation

> Updated: 2026-09-29, Slice 77 / Schema 59. These are executable local contracts and evidence-review workflows; research and content now have local persisted execution-simulation paths, but no real content/research evidence has been qualified and execution remains disabled.

## Slice 71 — Source-bound claim review and simulation budget receipts

The extended content-review contract accepts a same-company authorized source catalog and rejects citations whose MissionInput ID, revision or digest is missing or changed. Human-sample evidence must bind a stored sampling-plan MissionInput and digest to the exact draft revision/body digest and a unique, non-empty set of draft critical claims, recorded by the independent checker. The contract deliberately sets no sample percentage or quality threshold.

Research protocol/results now include a fixed seed, declared budget, reported positive consumed units and simulation output digest. The exact dataset and method source revisions must be present in the same-company input catalog. Over-budget results, changed seeds and missing output digests are rejected. Negative outcomes continue to be valid research results. This validation trusts the caller's execution receipt; it does not execute a simulator or prove the reported resource consumption.

The source-bound content and research contracts now have persisted local operation paths. Research runs only the deterministic `bootstrap-mean-difference@1` method; content publication records only a local simulation receipt with no external side effect. Neither path determines real domain quality nor enables profile execution. Valid `inconclusive` content and research outcomes remain inconclusive when their binding checks pass. Real domain evidence and runtime qualification remain open; profiles stay `not_run` and execution stays disabled. See `docs/implementation/R3_RESEARCH_SIMULATOR_FOUNDATION.md`, `docs/implementation/R3_CONTENT_OPERATIONS_FOUNDATION.md`, and the Slice 77 evidence.

## Content operations

`content-operations@1` separates authorized sources, versioned drafts, independent fact-check, human sampling, simulated publication, corrections and feedback. A fact-check binds to one draft revision; a later edit makes the check stale. Verified critical claims require source input/revision/hash references. Missing or conflicting sources remain inconclusive, and contradicted claims are rejected.

## Research simulation

`research-simulation@1` pins a dataset revision/hash, method digest, control definition and positive risk budget before evaluating a result. Researcher and evaluator must differ. Positive, negative and inconclusive outcomes remain distinct; negative results can be accepted as valid research when their protocol and evaluation evidence are complete. This profile only accepts simulation mode.

## Qualification evidence gate

Each reference profile declares its own required evidence areas. Content operations requires quality, human intervention, recovery, cost and organization-benefit evidence. Research simulation requires quality, recovery, cost and organization-benefit evidence. Each submitted area binds a same-company MissionInput ID/revision/content hash, the assessment-method digest and the assessing employee. The Kernel verifies the input revision/hash exists in that company and verifies the assessor is a company employee. Submissions must match a known profile revision and include each required area exactly once to become ready for review.

`EvaluateDomainEvidence` reports `incomplete`, `rejected` or `ready_for_review`. Schema 29 stores accepted incomplete and ready-for-review submissions in an append-only company ledger, with normalized child rows referencing the exact MissionInput revision and employee. The Workbench can read the ledger and submit evidence references. RequestID replay is idempotent, and readback checks the digest and JSON/normalized-row correspondence. Nil evidence lists normalize to an empty JSON array before recording; database checks also require the evidence array and profile identity to match the stored columns. `ready_for_review` only means evidence references are structurally complete; it does not judge the underlying result, invent a numeric threshold, qualify the profile or enable execution. Database constraints require `qualification_status=not_run` and `execution_enabled=false` for all records.

The form stores references, not duplicate evidence bytes. Operators first upload evidence as a MissionInput, then submit its ID, revision and digest. Reviewers can inspect a verified list of files in each referenced package and request one bounded preview per evidence area. Listing and preview require the same company, record, area, MissionInput revision and source digest; the Kernel also loads the selected file from CAS and checks its size and content digest. Text/Markdown/CSV/JSON is displayed as text, and PNG/JPEG is displayed as an image. PDF originals are not embedded or executed; only a parser-produced extracted-text file can be previewed, and extraction/source metadata remains unavailable as evidence content. Unsupported and metadata-only files are explicitly marked unavailable.

## Independent evidence-reference review

Schema 30 adds one append-only review decision per submission. The allowed outcomes are `evidence_references_accepted`, `evidence_references_rejected`, and `more_evidence_required`; each requires a rationale of 1–2000 characters. Only a company employee with `role_name='review'` may decide, and the reviewer must differ from every employee listed as an assessor. The Kernel checks these rules inside the write transaction. The database trigger independently checks submission readiness, reviewer role and assessor separation; it takes a `FOR SHARE` lock on the reviewer row so a concurrent role change cannot pass the check. A submission can have only one decision. RequestID replay is idempotent, and a second decision requires a new evidence submission.

Schema 31 adds `previewed_evidence` and `review_contract_revision`. New decisions must bind at least one safe, allowlisted preview to every evidence area and persist its relative path, source digest, content digest and media type. The Kernel re-reads each selected path from CAS and verifies the bytes at decision time; the database trigger validates area/source correspondence, path safety, media type, uniqueness and coverage. The trigger cannot read CAS, so byte-digest verification belongs to the trusted Kernel write path. Reserved PDF extraction and Git provenance metadata paths are unavailable for every source kind, consistently in listing, preview, Kernel validation and the database trigger. Prior Schema 30 decisions remain available at contract revision 0 with no preview attestations. The Workbench requires a successfully loaded preview for each area before enabling review and submits those attestations; the server remains authoritative.

The decision is strictly about evidence references and the bytes that were previewed. Accepting references does not accept the evidence result, establish substantive domain quality, qualify a profile or enable execution. Both profile tables and every submission keep `qualification_status='not_run'` and `execution_enabled=false`. The review POST route is protected by the desktop session token, including tokenless loopback mode; preview responses are `no-store`, `nosniff`, content-length bounded and expose only the headers the desktop frontend needs to verify the source binding.

## Per-submission substantive area review

Schema 38 adds one immutable substantive assessment per ready evidence submission, separate from the existing reference-integrity decision. It is accepted only after a `review`-role employee has accepted the preview-bound reference review. The substantive reviewer must differ from each area assessor and must submit a fresh preview attestation per required area; the Kernel re-reads each selected CAS file and checks the source/content digests and media type at decision time.

The reviewer records `accepted`, `rejected`, or `insufficient` with a bounded rationale for every profile-required area. Content operations requires quality, intervention, recovery, cost and organization-benefit decisions; research simulation requires quality, recovery, cost and organization-benefit decisions. The overall per-submission result is computed from those area decisions: any rejection yields `evidence_rejected`; otherwise any insufficient area yields `more_evidence_required`; all accepted areas yield `evidence_accepted`. The trusted Kernel persists the immutable assessment plus normalized area rows. Database triggers verify role independence, prior reference review, evidence digest, profile-specific area coverage, preview bindings, normalized-row correspondence and the derived overall result; downgrade refuses to delete assessment history.

This result accepts or rejects only the exact submitted evidence package. It does not set reference-profile qualification, change the profile's `not_run` status, or enable domain execution. No real content-operations or research evidence was used or reviewed, so neither profile is currently qualified or available.

## Global profile qualification decision

Schema 49 adds an append-only company/profile qualification event, distinct from any single evidence submission. To record `qualified`, the owner references a same-company JSON MissionInput using `r3-domain-profile-qualification@1`. The report pins the exact profile revision and includes one or more accepted case references for every required area. Each reference carries the submission ID, evidence digest and substantive assessment ID; the Kernel re-reads the MissionInput from CAS and revalidates same-company scope, profile revision, accepted reference review, accepted per-area assessment and digest before recording the owner decision. A separate `revoked` event requires a current qualification. Schema 50 adds monotonic event ordering and company-row serialization so concurrent decisions cannot reorder.

The Workbench generates the bounded aggregate report from accepted case assessments and exposes token-gated owner qualify/revoke actions. The profile ledger shows `not_run`, `qualified` or `revoked` per company. `executionEnabled` remains false even after an evidence qualification because no content/research product runtime exists. Case-level review and software acceptance tests cannot create real domain evidence, numeric success thresholds are not inferred here, and no real profile has been qualified.

Global qualification and real content/research evidence remain incomplete. Each profile stays unavailable until its own quality, recovery, cost, organization-benefit and (for content operations) intervention evidence is collected and reviewed in domain-specific context, followed by separate runtime qualification.

Qualification stays `not_run` until domain-specific evidence is collected and reviewed; even an owner-qualified evidence profile cannot execute until a separate domain runtime is built and qualified.
