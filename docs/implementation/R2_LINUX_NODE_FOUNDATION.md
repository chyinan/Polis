# R2 Linux/Node execution foundation

Updated: 2026-09-30, Slice 89. Status: resource, disk-bound and instance-owned startup recovery code implemented; Linux WorkerSession cgroup v2 containment/recovery wired; not qualified for project use.

R1 remains native Windows/Node. This adds the original Linux/Node profile as a separate R2 implementation and preserves the v0.4.5 design snapshot.

## Implemented

- Schema 27 admits `linux-node-npm@1` separately from `windows-node-npm@1`. The Linux parser preserves case-distinct paths and uses the fixed `npm ci --ignore-scripts --no-audit --no-fund --offline` policy with `deny_all` network policy.
- `linux_bwrap@1` command plans use `--unshare-all`, `--die-with-parent`, and `--new-session`; mount the curated system image read-only; bind only the per-run workspace writable; clear the host environment; and do not use `--share-net`. Required `/proc`, `/dev`, `/tmp`, and `/workspace` mountpoints must already exist in the curated image.
- `linux-node-toolchain@5` binds the bubblewrap executable bytes, permissions and Linux UID/GID ownership; the complete curated image tree; fixed guest Node/npm paths; the selected offline npm cache; the delegated cgroup root path; default per-job CPU/memory/PID limits; and the configured maximum workspace filesystem capacity. The system-image digest includes entry type, permission mode, Linux UID/GID ownership, regular-file bytes and symlink targets; it refuses to fingerprint an image if UID/GID metadata is unavailable. After the first scan, it rechecks the exact path set and revalidates every entry identity and metadata, rehashing regular files. System-image and cache scans have entry and byte bounds. Cache symlinks and special files are rejected. A verified cache is copied into a fresh per-environment workspace, so project code cannot write back to the shared cache.
- Control has an opt-in Linux preparation executor with two active and eight queued admissions, snapshot verification, bounded output, timeout/stop handling, retained process handles, workspace cleanup, and the existing JobRun batch path. Linux and Windows executor profile support remains separate.
- The fingerprint command is `polis linux-node-toolchain-sha256`. It uses the same paths as `polis serve` and prints the digest needed when registering a Linux profile revision.
- When a pending preparation process exits, a workspace-removal error no longer clears its pending/handle records or releases the preparation slot. Cleanup retries ten times; if removal still fails, ownership remains recorded for a later service cleanup attempt.
- Each Linux install and batch JobRun receives a distinct cgroup v2 group. Defaults are 2 CPU cores (`cpu.max=200000 100000`), 2 GiB `memory.max`, `memory.swap.max=0`, `memory.oom.group=1`, and `pids.max=256`. The child is placed into the group atomically at process creation with Go's `UseCgroupFD` support. Workspace admission is atomically reserved across preflight and process launch registration to prevent concurrent JobRuns against the same workspace. The delegated parent must cap aggregate use to at most 4 CPU cores, 4 GiB memory, no swap, 512 PIDs, and 32 cgroup children, with group OOM handling. The executor verifies these existing parent controls but does not enable/change them. Cleanup kills only processes in the owned group and retains JobRun/preparation uncertainty if the group cannot be emptied and removed; a workspace with pending spawn-rollback cleanup rejects new JobRuns until cleanup is confirmed.
- Slice 89 also sets `cgroup.max.descendants=0` on each per-job group. This blocks creation of nested groups under a Worker/JobRun and keeps cleanup within the exact cgroup leaf. The Worker launch profile requires `--unshare-cgroup`, hides `/sys` behind tmpfs, and rejects host cgroup control-file binds; stop evidence includes the persisted host, cgroup-root and boot identities. These local checks do not replace a delegated-host escape/recovery qualification.
- Startup binds `POLIS_LINUX_NODE_RUNTIME_ROOT` to a private instance marker derived from the configured PostgreSQL server host/port, database name/role and BlobRoot. Credentials are excluded, so password rotation does not change the identity. Runtime and cgroup directory `flock` leases are held for the Workbench lifetime. The delegated cgroup root also holds a persistent empty `polis-owner-<identity>` child, so the same cgroup mount cannot be reused by a different server/database instance after a crash or through another runtime path. A nonempty cgroup root without an owner marker is treated as unowned legacy state and blocks startup for operator review.
- After owner verification, the manager accepts direct child `polis-node-` leaves for Node Jobs and `polis-worker-` leaves for WorkerSessions, each followed by 24 lowercase hex characters. Startup kills Node leaves and waits for recursive `cgroup.events populated 0`; it preserves Worker leaves for database-bound reconciliation, then removes only empty orphans. Unknown names, symlinks, foreign owner markers, or populated unknown Worker leaves stop startup before the HTTP listener opens. `cmd/polis` detects active or outcome-unknown Linux Node JobRuns, preparations and Linux WorkerSessions. Unresolved work requires the runtime and delegated cgroup roots; no command or Worker start is replayed. The root leases remain held until shutdown cleanup verifies that only the empty owner marker remains.
- The aggregate workspace disk bound uses a separate existing ext-family or XFS filesystem mounted at `POLIS_LINUX_NODE_WORKSPACE_ROOT`. The default maximum is 16 GiB; `POLIS_LINUX_NODE_WORKSPACE_MAX_BYTES` can set another positive byte bound. The filesystem must be on a different device from the Polis runtime root, curated system image, npm cache and delegated cgroup, and its total data capacity must not exceed the configured maximum. This turns the filesystem’s physical capacity into a hard aggregate ceiling for all workspaces. Polis never mounts/resizes the filesystem or alters the host quota settings. The check runs at startup, before preparation reads/materializes project data, before child process launch and before workspace cleanup; absent/replaced mounts fail closed.

## Configuration

Set these variables only on the Linux host running `polis serve`:

| Variable | Required value |
|---|---|
| `POLIS_LINUX_NODE_PREPARATION_ENABLED` | Set to `1` to install the Linux executor. Default is off. |
| `POLIS_LINUX_NODE_BWRAP_PATH` | Absolute path to the selected regular bubblewrap executable. |
| `POLIS_LINUX_NODE_RUNTIME_ROOT` | Existing service-owned, private Polis runtime directory dedicated to this local database and BlobRoot. A protected identity marker is stored here. |
| `POLIS_LINUX_NODE_SYSTEM_IMAGE_ROOT` | Existing curated Linux rootfs directory below the runtime root. |
| `POLIS_LINUX_NODE_WORKSPACE_ROOT` | Existing separate workspace directory below the runtime root. |
| `POLIS_LINUX_NODE_WORKSPACE_MAX_BYTES` | Optional positive integer byte ceiling for the workspace filesystem. Defaults to 17179869184 (16 GiB); the existing filesystem must have total capacity at or below this value. |
| `POLIS_LINUX_NODE_NPM_CACHE_ROOT` | Existing separate pre-populated offline npm cache below the runtime root. |
| `POLIS_LINUX_NODE_CGROUP_ROOT` | Existing dedicated cgroup v2 subtree mounted below the runtime root. Its `cpu`, `memory`, and `pids` controllers must be enabled for children; parent controls must cap aggregate resources and descendants to the fixed profile. The Polis service itself must not be a process in this delegated root. Startup writes a persistent owner cgroup before managing job groups. Roots with unbound legacy groups, a different owner, or unknown/linked children block startup without cleanup. |
| `POLIS_LINUX_NODE_PATH` | Optional guest executable path; defaults to `/usr/bin/node`. |
| `POLIS_LINUX_NODE_NPM_CLI_PATH` | Optional guest npm CLI path; defaults to `/usr/lib/node_modules/npm/bin/npm-cli.js`. |

The image, workspace, cache and delegated cgroup paths must not overlap. Guest Node and npm files must be regular files within the curated image, and Node must be executable. The fingerprint changes if bwrap or guest executable bytes, permissions or Linux UID/GID owners, image bytes, cache bytes, cgroup-root path, workspace disk ceiling, fixed resource limits or guest paths change. Recompute and re-qualify after any change.

## Instance identity upgrades

The owner marker version includes the PostgreSQL host/port. A root created by an earlier marker version has no server-endpoint proof, so startup deliberately refuses it instead of guessing which database owns its leftover groups.

To migrate a legacy root, stop `polis` and verify the old runtime marker at `POLIS_LINUX_NODE_RUNTIME_ROOT/.polis-linux-node-instance`. Inspect the direct children of `POLIS_LINUX_NODE_CGROUP_ROOT`. Continue only when the sole child is the matching old `polis-owner-<identity>` marker, both the delegated root's `cgroup.procs` and the marker's `cgroup.procs` are empty, and there are no `polis-node-*` or `polis-worker-*` leaves. Remove only that private runtime marker and empty owner cgroup, then restart with the intended PostgreSQL endpoint and BlobRoot; startup writes the new identity markers. If any job group, process or unknown child exists, leave the markers in place and reconcile ownership with the operator before restarting. Do not remove markers to work around a database endpoint or BlobRoot configuration mismatch.

## WorkerSession restart recovery

New Linux real Provider WorkerSessions use `linux_worker_cgroup_v2@1`. Control creates a stable opaque leaf derived from the session ID, persists it in an append-only `process_containment_bound` observation, then passes the leaf FD into Runner's atomic `UseCgroupFD` launch. Runner binds sandbox validation to the actual configured cgroup root and accepts only the exact ordered Worker bwrap argument profile emitted by its generator, including the expected writable home source; extra/reordered mounts and cgroup-root aliases are rejected. Stop sends `cgroup.kill` and waits for recursive `cgroup.events` to report `populated 0` before confirming stop. Startup preserves Worker leaves while cleaning Node JobRun leaves, binds the candidate to the exact deterministic leaf, clears it, and appends cgroup-bound host-reconciliation evidence without replaying `Worker.Start` or a provider action. Empty unreferenced Worker leaves are removed; populated unknown leaves block the listener. If startup finds a legacy `linux_process_group@1` record, it may adopt it only when that session's exact Worker cgroup leaf exists and is emptied; otherwise the session remains unresolved.

This is offline software evidence. No delegated cgroup v2 host was exercised. Qualification must verify that the Worker process cannot write `cgroup.procs` or otherwise migrate out of its cgroup, along with exact-host cleanup and a real multi-day Worker run. The authoritative Task workspace digest/revision is persisted in PostgreSQL/CAS and rehydrated by a fresh WorkerSession; mutable files from an `outcome_unknown` project JobRun are not restored or replayed.

## Qualification boundary

The executor is opt-in, but this change did not create a qualification event. Kernel preparation still requires a qualified `linux-node-npm@1` executor fingerprint and exact `linux_bwrap@1` isolation profile, plus the separate approved project policy. Therefore the ordinary API remains blocked until independent evidence is reviewed and recorded.

Tests use fake launch/process objects, temporary cgroup directories and filesystem snapshots. They verify identity stability across password rotation, rejection of another host/port/database identity, exclusive leases, owner-marker persistence, no cleanup of unbound legacy groups, and cleanup limited to managed names. The R2 disposable PostgreSQL fixture checks active Linux JobRuns/preparations require a recovery root while terminal records do not. No bubblewrap process, npm command, project script, live registry, real Worker/model, QQ, MCP, GitHub account or business data was used. Cgroup launch and restart code and the workspace capacity guard remain unqualified on a delegated cgroup v2 host with a dedicated ext-family/XFS workspace volume. No actual workspace mount was created or changed. Namespace/rootfs qualification, cache completeness, clean-VM operation, service health probes, and multi-day host evidence remain open. See Slice 22's baseline, Slice 27–31 follow-up, and Slices 57–58 evidence under `evidence/development/`.
