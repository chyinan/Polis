# Slice 157 — CAP-20–24 MCP state, result and outcome audit

Date: 2026-10-03
Scope: read-only source audit of frozen CAP-20–24. No source, schema, endpoint, account or WorkerSession was mutated. The user-approved Worker rule remains: admit calls only through the database-confirmed active WorkerSession and its exact Company/Employee binding.

## Findings

- **CAP-20 — stateful external handles across Companies/Employees:** `stdioMCPWorkerState` owns one process per WorkerSession and pins it to one capability, transport, qualification and endpoint; the process is stopped with that session (`internal/control/stdio_mcp_worker.go`). Every call is authorized against the bound Employee's current capability event and runtime qualification under the Company lifecycle guard (`internal/kernel/mcp_runtime_qualification.go`, `internal/kernel/mcp_worker_context.go`). This demonstrates Polis-side authorization and process ownership. It does not demonstrate that a remote Streamable HTTP service separates its server-side browser/business handles by Company or Employee. HTTP credential/OAuth identity is not currently captured. Keep CAP-20 open for each external stateful service until a distinct employee-bound endpoint/credential or equivalent provider evidence demonstrates isolation; a handle is never identity or authorization.
- **CAP-21 — server-initiated requests and `input_required`:** stdio client capabilities are empty and its response reader rejects messages containing a server method (`internal/mcptransport/stdio.go`). The Streamable HTTP SSE parser ignores notifications but rejects server requests with an ID or any response that fails to match the current request (`internal/mcptransport/streamable_http.go`). The stdio result parser admits only `resultType == "complete"`; HTTP requires bounded text content and rejects structured content, so an input-required shape without that content fails (`internal/mcptransport/stdio.go`, `internal/mcptransport/streamable_http_contract.go`). Unsupported/failed results cause the current Worker call to fail and stop rather than automatically invoking a model, granting authority or retrying (`internal/control/real_provider_worker.go`). This is source evidence only; CAP-21 remains `not_run`.
- **CAP-22 — resource links, media, HTML and oversized results:** both controlled result profiles admit bounded text only (64 KiB aggregate). Structured content, resource/media blocks, malformed content and oversized results fail closed; neither result adapter fetches resource links or executes returned content (`internal/mcptransport/stdio.go`, `internal/mcptransport/streamable_http_contract.go`, `internal/kernel/mcp_tool_call_contract.go`). HTML in a text block remains untrusted text passed through to the provider; Polis does not render it as HTML. Result storage binds the tool name and qualified schema digest and persists the result digest. There is no truncation path, so oversized results are rejected rather than silently truncated. CAP-22 remains `not_run` pending scenario execution and external UI/provider review.
- **CAP-23 — write timeout, cancellation and error results:** a durable `dispatching` intent is reserved before the remote call and keyed to Company + WorkerSession + provider call ID (`internal/kernel/mcp_tool_calls.go`). Stdio requests time out after 30 seconds; cancellation notification write is best-effort for 250 ms before the process stream is closed. Streamable HTTP uses a 45-second client timeout. HTTP/JSON-RPC errors and tool `isError` results fail; call failures block the WorkerSession. On session stop/reconciliation, pending dispatches transition to `outcome_unknown` (`internal/control/stdio_mcp_worker.go`, `internal/kernel/mcp_tool_calls.go`). No automatic retry or success inference occurs. This does not prove whether an external side effect happened; it requires reconciliation evidence. CAP-23 remains `not_run`.
- **CAP-24 — hidden service AI cost/retries:** MCP protocol calls and result bytes are observable at the Polis boundary; remote model tokens, retries, prices and settled spend are not. Existing provider retry observations are explicitly limited to surfaced same-turn reconnect signals, with unobserved retries recorded as unavailable (`internal/provider/codex_runtime.go`; `evidence/development/r1-r3-implementation-validation-20261003-slice-128-provider-retry-visibility/verification.md`). The service boundary therefore supports only a limited protocol-activity statement, not a strict total cost cap. CAP-24 remains `not_run`.

## Qualification and execution limits

This was source inspection, not a frozen scenario run, live PostgreSQL concurrency qualification, real MCP endpoint exercise or billing measurement. CAP-20–24 `execution_status` values remain `not_run` in `spec/design-v0.4.5/tests/capability_scenario_catalog.json`. The concrete outstanding evidence is external per-employee handle isolation for stateful HTTP services, plus provider-side cost/retry visibility. No code change is justified by local source evidence alone: these gaps require an external service contract/identity or provider/account evidence, not a local claim.
