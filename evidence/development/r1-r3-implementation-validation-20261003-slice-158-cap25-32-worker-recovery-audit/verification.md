# Slice 158 — CAP-25–32 Worker continuity and recovery audit

Date: 2026-10-03
Scope: read-only source audit of frozen CAP-25–32. Every Worker action remains confined to its database-confirmed active WorkerSession, Company, Employee, Task and current epoch. No source, schema, account, endpoint or WorkerSession was mutated.

## Findings

- **CAP-25 — change model inside one harness:** the native Codex app-server starts a fresh ephemeral thread with the selected model, a fixed versioned Polis tool list, read-only sandbox and `allowProviderModelFallback=false` (`internal/codex/client.go`). A new admitted WorkerSession increments the Employee epoch; Skill/MCP calls read exact current bindings and immutable revisions/digests from the database (`internal/kernel/worker_state.go`, `internal/kernel/capability_skill_runtime.go`, `internal/kernel/mcp_worker_context.go`). A prior provider thread or in-memory MCP owner is not copied. Model-specific behavior and successful Skill/tool recovery are not qualified; CAP-25 remains `not_run`.
- **CAP-26 — change to a different harness:** the repository has a fixed Codex runtime and a zero-egress Fake control fixture, but no second native business harness or cross-harness capability converter. Provider admission checks the selected model/profile, exact tool-surface fingerprint and current WorkerSession before start (`internal/provider/authorization.go`, `internal/control/real_provider_worker.go`). Unsupported harnesses cannot be selected through a fallback path; equivalent capability substitution is not implemented. No automatic repository-wide scan is used to fill missing capabilities. CAP-26 remains `not_run` and cross-harness behavior is unsupported pending a separately qualified adapter.
- **CAP-27 — read-only handoff asks for script/write/collaboration:** no script runner is exposed on the Worker surface. Database-bound writes require the current active session, matching Employee epoch/incarnation and active Mission; `checkSession` also calls `requireMemoryTaskWritableTX`, which blocks frozen Tasks. Collaboration paths require clean memory state (`internal/kernel/worker_state.go`, `internal/kernel/memory.go`, `internal/kernel/collaboration.go`). An old WorkerSession cannot be reused after stop/recovery, and product-provider successor admission requires stopped prior sessions and owner-reviewed Task memory revalidation. A new session receives a fresh Employee epoch. This supports fail-closed admission in source; CAP-27 remains `not_run`.
- **CAP-28 — revocation during MCP work:** each controlled MCP call holds the per-Company/server advisory lock from authorization through durable result completion. Capability/Employee revocation uses the same server lock and appends durable revocation/session snapshots; after acceptance, Control stops the exact affected WorkerSession and marks a pending intent `outcome_unknown`. New calls re-read current capability, runtime qualification, Employee binding and active WorkerSession (`internal/kernel/capability_source_import_lock.go`, `internal/kernel/capability_governance.go`, `internal/kernel/mcp_runtime_qualification.go`, `internal/kernel/mcp_tool_calls.go`, `internal/control/capability_revocation_stop.go`). The lock uses a nonblocking try: a revoke racing a held call returns conflict without committing and must be retried after the call releases the lock. This avoids inverting the Company-row and server-lock order. CAP-28 remains `not_run`; timing, queued callers and external side effects need scenario evidence.
- **CAP-29 — Employee sleep and idle MCP reclamation:** schedule reconciliation treats an active WorkerSession as `working` and an admitted one as `admitted`; `sleeping` requires no actionable work or live/admitted session (`internal/kernel/employee_schedule.go`). The only automatic product admission loop requires the zero-egress Fake @7 runtime and is opt-in (`internal/control/automatic_worker_dispatch.go`). MCP process/client ownership is local to one WorkerSession and `cleanup` stops it before releasing the owner lease (`internal/control/real_provider_worker.go`, `internal/control/stdio_mcp_worker.go`). There is no shared idle MCP pool. Source does not define a separate idle timer for a live provider session; CAP-29 remains `not_run` and needs lifecycle/host qualification.
- **CAP-30 — notification/discovery flood:** Polis does not subscribe to or host an inbound MCP notification stream, so MCP events cannot fan out Worker wakeups. Calls use request/response with matched IDs; tool discovery is rechecked before each call and bounded to 64 pages, 64 tools, 2 KiB per cursor and 256 KiB aggregate, with per-operation deadlines (`internal/mcptransport/stdio.go`, `internal/mcptransport/streamable_http.go`). Worker dispatch is separately opt-in, zero-egress Fake-only and database-keyset bounded. No unrelated MCP notification wake path exists. CAP-30 remains `not_run`; no flood qualification was performed.
- **CAP-31 — recovery package with missing Skill bytes or stale tools/handles:** backup refuses active WorkerSessions, Jobs, preparations, uploads, service leases and notification sends; it captures the PostgreSQL database and verified full CAS inventory and excludes provider/external credentials. Restore requires an empty target, restores into a new CAS root and does not activate the service configuration (`internal/recovery/backup_create.go`, `internal/recovery/backup_restore.go`, `docs/implementation/R2_RECOVERY_BACKUP_RESTORE.md`). Kernel recovery increments Employee epochs and marks non-stopped WorkerSessions `reconcile_required`; it does not replay their provider work. Skills/MCP are addressed by exact IDs/revisions/schema digests; Skill reads verify exact CAS members, stdio runtime qualifications outside the current sandbox are revoked, and Streamable HTTP is behind an opt-in environment gate and rechecks the live schema (`internal/kernel/recovery.go`, `internal/kernel/capability_skill_runtime.go`, `internal/kernel/mcp_runtime_observation_intent.go`, `internal/control/real_provider_worker.go`). **Residual:** the restored database retains historical global approvals and Employee capability-binding events. Source review does not establish that every restored binding requires a new owner receipt before a later, explicitly admitted WorkerSession can use it. CAP-31 remains `not_run` and this policy needs a recovery-generation scenario/decision; no same-name fallback or credential restore was found.
- **CAP-32 — four-role end-to-end closeout:** the repository contains bounded fake collaboration, Artifact reads, handover, approval, validation, budget and intervention ledgers, but its real product Worker admission is pinned to a fixed surface/profile and one product-executable Task. The frozen four-role sequence has not been executed with real approved Skills/MCP, a qualified provider/runtime, human-intervention review and settled cost evidence. Hidden provider/service spend remains outside current observations. CAP-32 remains `not_run`; source foundations do not constitute a completed end-to-end result.

## Qualification and execution limits

This audit does not modify or execute any frozen scenario. CAP-25–32 `execution_status` values remain `not_run` in `spec/design-v0.4.5/tests/capability_scenario_catalog.json`. No live PostgreSQL WorkerSession, model, harness, endpoint, backup restore, host process, event flood or provider/account billing measurement was exercised. The explicit software follow-up is to settle the restore-generation authorization policy for retained MCP bindings; model/harness, idle-session, external service and full-chain claims still need their separately qualified evidence.

No migration or test was run. `git diff --check` is the only validation for this documentation-only slice.
